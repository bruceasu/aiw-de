# Large Issue decision dependencies

Load only when several material decisions depend on one another or discovery
must continue across sessions. Read Decision dependencies in the entry-declared
`../skills/workflow-methods.md`; the Skill entry supplies this installed shared
resource. Small clear Issues need no map or extra stage.

Keep a compact section in this same Issue Plan, not a separate document/tracker:

```markdown
## Decision dependencies

Destination: user outcome and boundary of this effort.

| Question | Prerequisites | State | Evidence / answer owner | Next step |
| --- | --- | --- | --- | --- |
| D1: What does completion mean? | none | open | Issue rules | clarify outcome |
| D2: Which acceptance proves it? | D1 | blocked | Issue acceptance | wait for D1 |

Not yet clear: in-scope areas not precise enough to frame as questions.
Out of scope: deliberately excluded work and why.
```

Question IDs are local references, not Issue IDs, statuses or Work Items. Follow
the existing supported capture/confirmation process for Plan edits; text notes
do not authorize mutations or approve children. Read current decisions/frontier
on resume, zoom into sources only for the next question, preserve prior answers
and link the authoritative conclusion. An empty frontier with unresolved blockers
is not readiness. Do not pre-ticket fog or duplicate answers in a second map.

Use the already selected grill-with-docs/grilling conversation method for the
current question under host limits. Do not run another full interview, automatically
spawn research agents or ask the human for facts available in authorized evidence.
Human-only choices remain unresolved until actually answered.

Questions alone do not become child deliverables. Use existing business outcome
splitting rules for genuinely independent child Issues; Planner later owns the
engineering design and ordered Work Items. Carry remaining engineering questions
and links into the same FD, not a new proposal/task map. Business acceptance gaps
must be resolved before approval/handoff; they cannot be relabeled engineering.

Complete when material in-scope business decisions and acceptance are settled,
or return a precise blocked/incomplete result with remaining dependencies and
independent work that can continue. No mandatory one-question-per-session limit
or new gate beyond the existing Issue readiness/confirmation rules.
