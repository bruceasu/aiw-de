# Intake handoff summary

Load only when a request needs a durable routing summary. The historical
filename does not make this an authoritative execution specification. It is
input to Issue Management or review; Issue Plan owns software requirements,
FD owns engineering design/Work Items. Do not duplicate their acceptance lists.

```markdown
## Intake handoff

Source: title, stable ID/link and relevant evidence revision/date.
User problem and desired outcome: preserve the original need.
Known facts: separate reported claims, static observations and confirmed facts.
Missing information: specific unresolved questions, not generic more-info asks.
Related work: candidate duplicates, existing Issue/FD/spec links and differences.
Impact / suggested priority: concrete reason, not an invented score.
Next action / owner: clarify in Issue, inspect PR, request information or defer.
Existing decisions: authoritative links, including rejection/deferral context.
```

Include evidence paths/revisions when useful for traceability; do not prescribe
line-by-line implementation. Proposed rules are not approved facts. Avoid a
second code checklist, copy of FD decisions or automatic ready-for-agent verdict.
A summary may include observed symptoms and candidate acceptance examples,
clearly proposed for the owning Issue to refine and confirm.

Prepare locally by default. Only publish to a tracker when explicitly authorized
for that action; preserve the triage disclaimer and report the actual result.
