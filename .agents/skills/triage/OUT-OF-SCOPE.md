# Prior scope decisions

Load only relevant known decisions for a candidate match, not every historical
file. Prefer linked Issue decisions as the authority. Existing .out-of-scope/
notes may be consulted when relevant, but do not create a second rejection
database by default or automatically migrate/delete historical notes.

Distinguish:

- Already satisfied: confirm the original user need is actually met; point to
  evidence. Existing code alone may miss behavior, access or documentation.
- Duplicate: identify the authoritative related request and meaningful differences.
- Deferred: potentially valid, postponed for a stated reason or prerequisite.
- Rejected/out of scope: an explicit decision with scope, rationale and source.

A prior rejection is context, not automatic rejection of a new request. Check
changed constraints and whether the concepts actually match. Preserve earlier
rationale and history when reconsidering; add a linked superseding decision
within authorized scope rather than deleting the old record.

Return the match, uncertainty and next action to the host. Issue Management
owns individual business decisions under its normal confirmation rules. External
comments/closing and durable file changes require their respective explicit
scope; sorting a queue does not grant them. Never store secrets or credentials
in notes, or claim a proposed close has already happened.
