# Intake Triage

Follow `skills/reviewed-skill-contract.md`, `skills/work-management.md` and only
Intake queue in `skills/workflow-methods.md`. Use when the user asks to sort a
backlog, consolidate reports or route incoming requests. A named item can be
summarized for routing; detailed requirements belong to issue-management. No
mandatory triage step before an ordinary Issue or FD.

## Inputs and output

Use the requested queue/items, supplied reports or authorized tracker access,
existing Issue/FD links and local label/priority conventions. Return a compact
queue table: source/title, user problem/outcome, confirmed facts, missing
information, duplicate/related candidates, impact/priority reason and next
owner/action. Mark unresolved matches and incomplete sources explicitly.
Use source links and stable IDs; no invented Issue IDs or claimed readiness.

Read existing notes/replies before asking questions. Surface important new
information without repeating settled questions. If a source is unavailable,
report INCOMPLETE for that item and continue the others; do not probe network
or permissions. Load [AGENT-BRIEF.md](AGENT-BRIEF.md) only when a durable handoff
summary is useful, and [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) only for prior decisions.

## Routing and evidence

- Check only relevant authorized local records/code for duplicates, existing
  capability and previous decisions. Existing implementation may still leave
  a usability, documentation or behavior gap; do not automatically close it.
- Distinguish satisfied, duplicate, deferred and rejected with evidence. An
  earlier rejection can be reconsidered; preserve its original rationale.
- Route one item's problem/value/rules/acceptance discussion to issue-management;
  use its domain/grilling methods there instead of a second full interview here.
  Retain the user's original goal when producing software requirements.
- Route engineering design to fd-workflow and PR correctness to independent
  code-review/fd-review as applicable. An external PR is a source of intent
  plus a diff, not proof of acceptance or readiness to merge.
- Static code tracing can support a hypothesis, not claim runtime reproduction.
  No checkout, implementation, test, deployment or subagent work is implicit.

## Labels and external actions

Local tracker labels are optional recommendations, not a new state machine or
FD status. If an existing mapping uses needs-triage/needs-info/ready-for-agent/
ready-for-human/wontfix, preserve its vocabulary but explain the next action:
ready-for-agent means a scoped next action is described, not FD design-ready
or authorization to implement; ready-for-human names the required human decision,
not permission to merge. Conflicting labels are reported without speculative edits.

Default output is a local recommendation. Network reads and external labels,
assignment, comments or closing require the repository's explicit authorization.
Honor authority already supplied for those exact actions without another approval
loop; otherwise prepare the concrete proposed action, do not send it. If an
external comment is authorized, prefix it with:

> *This was generated by AI during triage.*

No automatic closure, issue promotion, glossary/ADR writes or rejection database
creation. Recommendations and handoff summaries are not approvals or execution
specifications; the Issue Plan and FD retain their existing ownership.

Complete when requested items have sourced summaries, unresolved information
and clear next actions, plus outcomes of any specifically authorized tracker
operations. State commands actually run, missing access and skipped runtime
checks. Never present local recommendations as applied external changes.
