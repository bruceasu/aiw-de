## 术语说明

已确认统一术语：

- Worker：团队中实际承担任务的成员，具有身份、能力、知识和经验；进程是其运行载体，不等同于成员本身。
- Agent：描述具备模型与工具循环的通用技术概念，不据此另设一类团队成员、接入流程或权限模型。
- 秘书：面向用户的助手和 Plane 管理入口，其连接职责与执行任务的 Worker 分开讨论。

现有代码中的 Agent 身份管理与 Worker 执行注册并非完全相同，以上是已确认的简化设计，不表示当前实现已经统一。“Agent 工厂”现有名称暂保留，是否更名尚未决定。

## 01：许愿池

已确认定位：将用户模糊的想法、需求，转换成可实施的软件需求或可执行的流程，最终生成计划。

已确认的最小流程：

1. 用户说出想法或需求。
2. 通过讨论澄清必要信息，逐步整理需求或流程。
3. 展示整理结果与计划草稿，用户可以继续修改。
4. 用户确认后生成计划，交由计划功能管理和执行。

已确认的专业参与要求：

- 由专业 Agent/Worker 参与讨论、需求整理和计划准备，具备完成当前工作所必需的 Skills。
- 参与者需要理解需求所涉及的现有系统，结合其功能、约束及关联关系提出方案。
- 系统知识通过知识库逐步扩展；Skills 提供工作方法，知识库提供系统事实和背景。
- 上述知识库扩展是已确认的建设方向，不代表当前已有完整知识或接入能力。

实现建议，待具体梳理：按当前需求读取相关系统知识；缺少关键资料时明确说明并向用户澄清，避免把推测当作系统事实。专业参与不预设固定的多 Agent 流程，按实际任务需要选择参与者。

已确认的附件要求：附件为可选输入，用于补充澄清需求，也可以本身就是原始需求。用户可以直接提供附件开始需求整理，无须先将内容重新描述为文字；参与讨论的 Agent/Worker 应结合附件和用户说明理解需求，必要时继续澄清。

已确认取消独立的“方案推荐”功能。需求分析、方案讨论和计划草稿生成直接融入许愿池讨论流程，无须另行发起推荐、应用推荐。

### 许愿池形象与本地化

已确认的设计方向：中文版借用“向王八许愿”的戏谑感，使用卡通鳖／甲鱼形象，不能画成硬壳乌龟；英文、日文采用较正常的、负责愿望的神祇形象。

中文版名称以“许愿王八”为方向，“许愿鳖”可作为含蓄备选。造型体现扁平软壳、长脖子和尖鼻子，气质呆萌、办事一本正经；幽默来自形象与互动，不嘲讽用户或其需求。英文可采用愿望精灵、日文可采用原创愿望神祇，避免生硬翻译中文笑点。具体美术稿与外文称呼待确认。

不同形象共用同一套需求澄清和工作流生成功能，不分别建设功能实现。沿用现有界面样式，形象不遮挡需求内容和实际执行状态。当前仅记录创意，未生成素材或修改界面。

## Plan：定位讨论

用户明确的方向：

- 当前名称为 Plan，实际希望承载的是 LLM 参与的工作流。
- 对难以用固定规则、决策树表达的部分，利用 LLM 的推理能力完成判断。
- 软件开发只是当前使用场景；用户认为现有实现用于软件开发过程的价值不大，需要重新审视定位。

已确认的能力目标与实施原则：

- 首期：工作流的步骤与可选分支明确，LLM 在指定节点理解输入并作出判断，决定后续分支。
- 进一步目标：希望 LLM 更智能地参与工作流，包括根据实际情况调整后续流程；具体自主范围仍需明确。
- 不强制拆为首期、后期。由实施者结合现有代码、复杂度和可维护性判断；若可以用简单实现一次完成，则优先一次完成。只有确有必要时才分期，不为未来能力提前增加抽象层。

已确认的呈现要求：工作流应以可视化方式呈现，便于理解流程。

建议的首期呈现范围，待确认：展示开始与结束、执行步骤、LLM 判断节点及带条件的分支；执行时标出当前步骤、已走路径和等待人工处理的位置。点击节点可查看输入、判断依据摘要和结果。可视化呈现不预设必须提供拖拽编辑器。

待讨论的设计建议：工作流描述目标、必要步骤及约束，明确哪些环节由程序执行、哪些环节交给 LLM 判断。LLM 判断应给出后续可执行的结果，而非只产出分析文字。

尚未决定：是否更名、采用哪些具体使用场景、可视化的编辑方式、后期 LLM 可以调整哪些步骤或分支，以及现有软件开发专用流程如何取舍。暂不据此新增工作流引擎或修改实现。

### 现有实现与难度初评

静态核对了 `workflow/graph/` 和 `workflow-graphs.html/js`：

- 已有任务、条件、跳转、人工提问、结束节点，以及执行记录和修改尚未激活子范围的能力。
- 当前条件只比较任务结果中的固定字段，如成功状态、评审结论和修改文件数，并非直接让 LLM 理解业务内容后选择分支。
- 当前图页面主要通过 JSON 编辑和展示数据，尚不是所需的可视化流程图。
- 图任务包含仓库、提交版本及专业执行配置，明显偏软件开发，不能直接视为通用业务节点。

初步判断：明确步骤下的 LLM 判断与流程图展示可以作为一次完整改动实现，现有任务执行与记录能力可选择性复用。支持通用业务输入、输出并摆脱软件开发专用约束，是核心改动。

有限的智能调整可一并评估：LLM 提议修改尚未开始的后续步骤，由用户确认后应用，保留已发生的执行记录。现有子范围修改能力不代表已经支持 LLM 自主改流程。完全自主地重写执行中流程的成本与风险更高，暂不承诺本轮实现。

本次是静态初评，未实施、未运行验证。具体范围在选定代表性业务场景后确定。

### 验证场景：客户售后申请处理

目的：用一个非软件开发场景，验证知识读取、LLM 业务判断、分支执行、人工补充和有限流程调整。以下规则和客户资料全部为模拟数据，不代表真实企业政策。当前只设计场景，不运行测试。

用户在许愿池提出：“帮我处理客户售后申请，按公司的规定整理处理建议；资料不足就询问我，特殊情况让我决定。”

**模拟知识库**

提供一份有版本标识的《售后规则》：

- 签收后 30 天内出现产品故障，可建议换货；超过 30 天，转人工决定。
- 判断前需要购买记录、签收日期、故障说明；涉及实物损坏时还需要照片。
- 疑似运输损伤时，需要补充核实包装和签收情况，不直接认定产品质量问题。
- 本流程只生成处理建议和回复草稿，不实际退款、换货或向客户发送消息。

日期计算使用样例明确提供的处理日期。缺少资料或知识库无法访问时，记录缺项并询问，不自行补造。

**最小工作流**

1. 接收客户文字与可选附件。
2. 读取《售后规则》和申请资料。
3. LLM 判断信息是否充分；不充分则列出具体缺项，等待用户补充，再重新判断。
4. LLM 根据规则和资料选择“符合换货条件”或“需要人工决定”，给出简短说明、引用的规则版本和资料依据。
5. 符合条件时生成换货建议与回复草稿；需要人工决定时，展示原因和可选处理方式，等待用户选择。
6. 汇总最终建议及仍需办理的事项，结束流程。生成建议不表示实际换货完成。

**可视化验收重点**

- 图上能区分执行、LLM 判断和人工等待节点，分支标出条件。

### Worker 成长与解散

已确认方向：

- Worker 可以持续成长，积累系统知识、工作经验和来自用户纠正的经验。
- Worker 具有稳定身份；执行进程重启不应丢失其身份和经验。共享系统知识与成员个人经验分别归属，按需使用。

建议的实现含义，待具体设计：提取内容可供人类筛选，有用部分可进入共享知识库或交给其他成员，不默认将全部记忆视为可信事实。解散应停止接收新工作，并明确处理在途任务；历史任务与结果保留，不能因解散成员而误删共享知识。提取、停用和永久删除的具体操作与数据保留规则尚未决定。

## 12：Agent loop

## 18：模型认证

用户提出的实现方向：ChatGPT 连接使用脚本语言处理，Control Plane 记录 Token 文件位置；目的是将外部协议变化与 Java 主程序隔离，避免协议调整时修改 Java。

已确认的 Python 与 Plane 分工：

- 使用 Python 处理 ChatGPT 登录、凭据导入、刷新及 Token 文件读写，将外部协议细节集中在脚本中。
- Plane 保存连接名称、类型、凭据文件位置与运行设备等必要信息，通过固定的本地调用约定启动脚本、取得状态；Java 不解析外部 Token 文件格式。
- 同一份凭据由统一入口协调刷新，避免多个 Worker 并发刷新旋转令牌；Worker 不各自实现刷新逻辑。
- 文件路径只对所属设备有意义。Plane 与实际调用模型的进程在同一设备时可使用本地文件；另一设备不能直接读取此路径。跨设备共享凭据不纳入当前实现范围。
- 脚本管理文件的安全保存，常规状态输出和日志不回显 Token。具体授权接口与凭据格式在实施前按官方契约核对。

边界说明：仅保存路径不足以完成连接管理；Plane 仍需要知道连接是否可用，并发起登录、刷新或断开等操作。协议实现归 Python，连接记录与用户操作归 Plane。

已确认的异机边界：不与 Plane 运行在同一设备的 Worker，自行管理模型连接与凭据，包括登录、导入、刷新和失效处理。Plane 不向异机 Worker 分发模型凭据，也不要求其读取 Plane 的本地 Token 文件。同机 Worker 可使用 Plane 协调管理的连接。模型运行信息和执行用量仍可按执行记录汇报，汇报不包含凭据。

当前仅记录已确认分工，未修改认证代码、执行登录或调用真实接口。

当前仅确认设计，未修改实现或运行采集及修复任务。

## 23：控制台登录

- 管理员仍需确认具体危险操作，登录不等于自动批准所有操作。
- 人类登录与 Worker 接入分别处理，不混用凭据。

## 24：Worker 接入

已确认：该项统一称为 Worker 接入，不另设 Agent 成员；秘书连接在秘书部分单独讨论。

已确认的接入规则：

- 外部 Worker 使用管理员创建的接入凭据，在所在设备配置后连接。

- 接入不逐次要求批准进程启动、能力登记等内部步骤；可执行操作范围归权限部分讨论。
- 异机 Worker 的模型连接仍由其自行管理。

## 25：Worker 权限

已确认的文件访问边界：默认不能访问工作区以外的文件和目录，除非有明确授权，或者用户直接指定。

按用户请求理解具体对象与操作：用户指定某个外部文件，不自动授权访问其整个上级目录；指定读取，不自动授权修改或删除。对已明确指定且含义清楚的操作，不因位于工作区外再次重复申请相同授权。

此前提出的其他权限简化建议仍待确认：成员可用工具、系统和资料构成能力范围，本次任务再明确实际操作对象与范围；Skills 和知识不自动增加权限。取消多层 Owner 绑定、计划托管、接管与归还等用户配置入口，超出范围时提出具体申请。危险操作的具体边界归第 26 项讨论。

当前仅记录设计，未修改文件访问或授权实现。

## 26：执行限制与危险操作确认

已确认的规则：

- 范围内常规操作自主执行：读取、创建、修改文件，运行任务所需的普通命令。
- 可恢复删除不逐次确认：工作区内文件移入回收区或保留备份，记录删除位置。
- 危险操作需要确认：不可恢复删除、大范围覆盖、破坏环境的命令、发布或向外发送数据。
- 已有明确授权直接执行：不为同一操作重复询问，也不将授权扩大到其他操作。
- 保留轮数和超时限制，触及限制时说明进展，由用户决定是否继续。
- 停止优先：收到停止请求后不再启动新操作，在途操作报告实际停止情况。

确认提示说明准备做什么、影响范围、能否恢复，提供“允许这一次／拒绝”。文件操作同时遵守第 25 项工作区边界。向模型提供本次任务所需上下文和执行已获准的正常联网工具，不因此逐次重新请求相同授权。

当前仅记录已确认设计，未修改执行限制或危险操作实现。

## 27：工作记录与可观察性

用户已确认要求：Worker 正在工作的内容需要记录，可以通过界面或 API 观察其状态和工作内容。

建议记录范围，待具体实现设计：

- 当前任务目标、所属工作流执行及当前节点。
- 当前状态、最近动作、更新时间；明确区分运行中、等待用户、等待授权、暂停、失败和已停止。
- 模型调用与工具操作的开始、结束、结果或错误，以及实际生成的阶段结果和交付物引用。
- 用户追加内容的接收与生效位置，控制请求与 Worker 确认情况。

界面与 API 使用同一份真实执行记录，支持查看当前状态及按时间查看过程。工作内容指实际输入、动作、可交付的说明和结果，不要求公开模型内部推理。缺少进度依据时显示当前动作，不编造完成百分比；连接状态与执行状态分开，最后一次记录不等于远端仍在执行。

已确认的成长用途：这些执行信息可用于持续改进 Worker 自身，与第 09 项的成长和经验记录关联。成功结果、失败原因、重试经历、用户纠正和人工决定，都是总结经验的依据。

建议复用同一份执行记录提取有用经验，并保留经验对应的来源；后续任务按需读取。记录不直接全部灌入记忆，不把一次失败或未经核实的模型说明自动当作通用规则。用户仍可查看、纠正和删除经验；修改 Skills、工具权限、模型配置继续遵循已确认的人工确认规则。

此前提出的一条执行时间线、直接显示具体失败原因、收起技术诊断、日志可导出等展示细节尚待确认。未修改实现或验证 API。

## 29：秘书对话

已确认的规则：

- 对话作为主要入口，用户直接描述事情，无须先创建任务。
- 简单问答直接回复；需要持续跟踪或执行时，再关联为任务。
- 多轮对话保留上下文，支持附件。
- 处理中可以继续补充内容、纠正方向，也可以暂停或停止。
- 清楚区分“已回答、已提交任务、执行完成”，不把回复结束当作工作完成。
- 关联任务后，可从对话直达执行详情，不在秘书内另做一套工作流管理。

秘书可以独立完成相当一部分工作，不仅是 Plane 的入口；具体边界按第 35 项补充要求理解。交给 Plane 执行时复用统一任务与 Worker 能力。当前仅确认设计，未修改秘书实现。

## 30：记忆与知识

已确认的用途划分：

- 个人记忆：用户偏好、长期约定和秘书积累的经验。
- 知识库：系统说明、业务规则、参考资料等可引用内容。

按当前任务读取相关内容，不把全部历史放入上下文。摘要用于压缩上下文，不代替原始记录。记忆支持查看、纠正和删除；知识保留来源。私人内容不自动进入团队共享知识库，确认共享后再提供给其他 Worker。

先做好资料导入、检索和引用，不提前建设复杂的知识管理体系。当前仅确认设计，未修改记忆或知识库实现。

普通问答不擅自创建报告或文件；确实需要保存时明确位置，并展示实际保存结果。工具失败直接说明原因；需要授权时提出请求并等待，不一律回答“处理发生异常”。

## 32：工作安排

用户指出 Spring Boot 易于增加周期性任务管理，据此撤回此前“周期性任务暂缓”的建议，将周期安排纳入设计范围。

建议支持马上执行、指定时间执行和周期执行，复用统一任务与工作流执行能力。周期安排保存时区，每次触发产生独立执行记录；修改或停用安排不等同于停止已经开始的执行。

建议先提供每天、每周等直观选项，无须另建完整的调度平台。重复执行重叠策略、停机错过后的处理规则待确认；已开始但中断的执行仍先核对实际结果，不因定时触发而重放。

已确认的调度分工：

- Plane／Spring 管理业务定时安排，包括工作流周期执行和价格更新。
- 安排、时区和下次执行时间保存在数据库；Spring 定期检查到期安排，创建正常执行记录，由现有 Worker 调度领取。
- 重启恢复与防止重复触发依靠数据库执行记录，不把内存定时器视为持久化任务管理。
- 操作系统负责开机启动 Plane、进程异常后重启等进程管理，不逐项注册业务安排。
- 不为此引入额外调度框架或新建独立调度平台。

当前仅记录设计方向，未修改调度代码或执行定时任务。

## 35：秘书独立工作与 Plane 协作

用户明确的要求：秘书可独立完成相当一部分工作。例如需求澄清可以复用许愿池能力，但不一定提交给 Plane；秘书也可以有轻量定时任务能力。

据此修正此前将秘书主要定位为 Plane 管理入口、持续工作必须交给 Worker 的建议。秘书应能在不连接 Plane 时完成自身能力和授权范围内的工作。

已确认的职责边界：

- 本地完成：需求讨论与整理、查询研究、授权资料和文件处理，以及轻量定时安排。
- 按需协作：用户要求团队执行，或需要完整工作流、其他成员能力时，再提交给 Plane。
- 共用工作方法、Skills 和适用的交互能力，不强制共用 Plane 的任务存储或在线服务；本地工作不自动上传。
- 轻量定时安排由秘书本地进程处理，保存本地安排；Plane／Spring 仍负责已提交给 Plane 的业务安排，不要求为了秘书独立使用而启动 Java 服务。
- 同一安排明确由本地或 Plane 负责，避免两边重复触发；本地服务停机时如何处理错过安排，待统一确认。

此前提出的本机自动登记管理权限、远程认证、最少内容提交和委派后跟踪等连接规则仍待此项具体确认。当前仅记录独立工作要求，未修改秘书、定时调度或 Plane 协作实现。

## 36：私有数据管理

已确认的规则：

- 正在执行或结果未确认的工作，先处理清楚再永久删除，避免丢失恢复依据。

保留必要的数据管理，不增加复杂的版本管理和同步系统。当前仅确认设计，未修改存储、备份或删除实现。
