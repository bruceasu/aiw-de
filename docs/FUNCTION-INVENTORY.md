## 术语与已确认的设计细节

- **Worker**：承担工作的团队成员，有稳定身份、能力、知识和经验；执行进程是运行载体，可以按需启动或复用。
- **Agent**：模型与工具循环的技术概念，不另设一套团队成员、接入或权限体系。“Agent 工厂”名称暂保留。
- **秘书**：面向用户的助手，可独立工作，也可按需连接 Plane 管理或委派任务。

### 03：工作流定位、定义与编辑

工作流描述目标、必要步骤及约束，明确哪些环节由程序执行、哪些环节交给 LLM 判断。LLM 判断应给出后续可执行的结果，而非只产出分析文字。

仍需明确：最终产品名称、后期 LLM 可以调整哪些步骤或分支，以及旧软件开发专用流程的具体退役范围。软件开发作为普通工作流应用的方向已确认。

#### 验证场景：客户售后申请处理

目的：用一个非软件开发场景，验证知识读取、LLM 业务判断、分支执行、人工补充和有限流程调整。以下规则和客户资料全部为模拟数据，不代表真实企业政策。当前只设计场景，不运行测试。

用户在许愿池提出：“帮我处理客户售后申请，按公司的规定整理处理建议；资料不足就询问我，特殊情况让我决定。”

**模拟知识库**

提供一份有版本标识的《售后规则》：

- 签收后 30 天内出现产品故障，可建议换货；超过 30 天，转人工决定。
- 判断前需要购买记录、签收日期、故障说明；涉及实物损坏时还需要照片。
- 疑似运输损伤时，需要补充核实包装和签收情况，不直接认定产品质量问题。
- 本流程只生成处理建议和回复草稿，不实际退款、换货或向客户发送消息。

日期计算使用样例明确提供的处理日期。缺少资料或知识库无法访问时，记录缺项并询问，不自行补造。

**最小工作流**

1. 接收客户文字与可选附件。
2. 读取《售后规则》和申请资料。
3. LLM 判断信息是否充分；不充分则列出具体缺项，等待用户补充，再重新判断。
4. LLM 根据规则和资料选择“符合换货条件”或“需要人工决定”，给出简短说明、引用的规则版本和资料依据。
5. 符合条件时生成换货建议与回复草稿；需要人工决定时，展示原因和可选处理方式，等待用户选择。
6. 汇总最终建议及仍需办理的事项，结束流程。生成建议不表示实际换货完成。

**样例与预期结果**

| 样例 | 输入 | 应观察到的结果 |
|---|---|---|
| A：资料齐全 | 处理日期 2026-11-12；11 月 9 日签收；有购买记录；客户描述“通电后无法启动”，希望换货 | 引用规则，选择符合条件分支，生成建议和草稿；不要求 Git 仓库，不实际发送或办理 |
| B：资料不足 | 有购买记录；客户说“收到后一直开不了机”，未提供签收日期 | 询问签收日期并等待；用户补充后沿同一次流程继续，已有步骤结果保留 |
| C：规则外情况 | 处理日期 2026-11-12；9 月 1 日签收；有购买记录和故障说明 | 转人工决定；用户选择结束处理时，不再自动重试或继续生成办理任务 |
| D：需要调整流程 | 初始文字只说“无法启动”；后续附件显示外壳破裂，并注明包装有挤压 | LLM 发现需要核实运输损伤，提出在未执行部分增加“核实包装与签收情况”步骤；用户批准后才加入并执行，拒绝则保留原流程并转人工决定 |

**可视化验收重点**

- 图上能区分执行、LLM 判断和人工等待节点，分支标出条件。
- 显示当前节点、实际已走路径；点击判断节点可查看资料依据、规则引用、结论和分支选择，无须展示模型内部推理。
- 样例 D 的新增步骤先以待确认状态呈现；批准后进入实际流程，原执行记录保持可查看。
- 暂停时不启动后续节点；取消或人工决定结束后不再自动推进。失败与等待用户回答明确区分。

这些样例用于后续实现验收，不要求为此建设订单系统、物流接口或新的知识库框架。

### 04：工作流管理

已确认的主流程：草稿 → 确认并启动 → 执行 → 完成。

已确认的执行控制：

- 等待用户：需要补充资料或人工决定时等待，回答后继续。
- 暂停／继续：暂停后不启动后续步骤；在途操作的停止能力需结合实际执行方式核对。
- 停止：结束整个工作流，保留已有结果。请求停止不表示在途操作已停止或已有副作用已撤销。
- 失败处理：展示具体原因，由用户选择重试当前步骤或停止；不得因此重复已成功的步骤。

已确认取消“人工标记完成、跳步、撤回”等独立入口；确有业务需要时，再作为含义明确的流程操作处理。归档、删除等记录管理细节尚未决定。

工作流定义与执行记录分开：定义可重复使用，每次启动产生独立执行记录。例如“售后处理”定义一次，每个客户申请分别执行。定义后续如何修改及影响哪些执行记录，待具体设计时确认。

FD-100 支持明确指定成员，停止接单时未领取工作等待、恢复后再领取。FD-101 补充默认自动选择：按节点声明的 Skills 匹配本人可接单成员，优先未完成工作少、最近工作较早的成员；不根据职责文字猜测能力。无成员、缺少 Skills 或匹配成员停接单时显示原因，满足条件后由现有周期任务继续。已选定节点的设定冻结，循环或重试不换人。用户仍可明确选择通用执行。旧匿名执行保持原意；连接中断结果核对等能力尚待统一。

### 12：Agent loop

已确认的统一循环：理解任务与完成条件 → 按需读取 Skills、知识和资料 → 调用模型 → 执行工具 → 根据结果继续或结束。

已确认的规则：

- 不同 Worker 共用同一套循环，差异来自任务、Skills、知识和工具。
- 判断节点输出明确的分支选择；执行节点交付实际结果。
- 缺信息时询问，危险操作申请确认，停止后不再推进。
- 对话式问题可直接回答，不强制调用工具或生成文件。
- 没有新进展或达到轮数上限时，报告已完成内容和阻碍，避免反复分析。
- 当前动作、工具结果和最终结论可查看，不把模型声称完成当作执行成功。

FD-102 已补充共享 SDK 循环的重复读取保护：先提醒，之后仍无新结果则在下一模型或历史摘要请求前停止，保留现场并说明原因。交替重复可识别，历史不重计，新信息／用户补充／可能的修改会重置；达到总轮数上限也有明确诊断。此规则不判断所有低质量回答，备用 app-server 未改。按需知识读取及其他循环改进仍待续；模型与推理强度的自动切换留到第 19 项。

### 13：执行工作台

已确认：统一为一份执行详情。从工作流、简单任务或团队成员进入时，直接打开对应执行，无须再次寻找。

默认展示：

- 正在做什么：当前步骤、最近动作、进度。
- 做了什么：模型交互、工具操作和结果，按时间展开。
- 需要用户处理什么：补充信息、授权或失败后的选择。
- 执行结果：交付物、完成情况、Token 和估算费用；缺失用量或价格不能展示为零。

暂停、继续、停止集中放在执行详情中，并明确控制范围。请求发出后显示“等待 Worker 确认”，收到回执后再更新状态。不再单独维护一套“专业配置工作台”。

用户补充的已确认要求：记录 Worker 正在工作的内容，通过界面或 API 都能观察 Worker 状态和实际工作内容。该要求同时适用于团队成员详情和执行详情，与第 27 项共用执行记录。

### 14：工作目录与交接

已确认的规则：

- 执行时可指定位置；未指定时，由 Plane 创建本次执行的临时目录。
- Worker 自行准备目录内容，按需要 clone、checkout 或创建 worktree。
- 同一次执行的成员共享约定位置，通过 `.ai/` 保存交接说明，不上传整份修改文件。
- 单 Git 仓库通常使用执行专属 worktree；多仓库目录不自动逐一创建。
- 相同目录只有具备可靠的 worktree 隔离时才并发，否则串行；不同目录可并发。
- 临时目录保留到整个工作流执行结束，再处理清理；失败时保留现场便于检查。

Plane 负责记录位置和分配临时目录，文件与 Git 的具体处理交给 Worker。

### 15：结果与评审

已确认的规则：

- 每个任务有明确的完成条件，Worker 提交实际结果和必要依据。
- 默认由执行 Worker 自检，不在每次完成后自动启动 Reviewer。
- 需要独立评审时，在工作流中明确放置评审节点，指定成员或所需能力。
- 评审输出“通过、需修改、需人工决定”，后续按工作流分支处理。
- 人工确认也作为明确节点，避免隐藏在多层完成门槛中。

“开发 → 评审 → 修改”与“售后建议 → 人工确认”使用同一套工作流表达。

### 16：人工问答、审批与执行中输入

已确认：统一到“待你处理”入口，并在对应执行详情中同步展示。

- 补充信息：说明缺什么，用户回答后继续。
- 业务决定：展示问题、依据和可选处理方式。
- 操作授权：说明具体动作、影响范围，以及是否仅授权这一次。

等待期间不重复提问、不反复重试。回答后继续原执行，拒绝或停止后按明确结果处理。执行中临时遇到问题也可以提问，无须预先为每个问题设计节点；流程图上显示当前步骤正在等待用户。

用户补充的已确认要求：Worker 执行中可以随时接收新内容，加入处理上下文；也可以明确指定在下一个 turn 生效。这是主动补充能力，不依赖 Worker 先发起问题。

建议的生效语义与展示，待实现设计：

- 区分内容“已收到”和“已用于执行”，记录收到顺序与实际应用位置。
- 立即加入上下文表示在当前执行后续可读取上下文的位置使用，不表示可以改写已经发出的模型请求。
- 指定下一 turn 生效的内容保留到下一次模型调用时提供，明确显示尚待生效；模型调用与工具执行的回合边界需在实现中统一。
- 追加文字不自动代表危险操作获准，也不自动重放已完成工作；停止后不因追加内容自动恢复执行。

### 17：模型连接

已确认的路径：

- 主要路径为 OpenAI 兼容接口，由我们自己的 Agent loop 调用模型，支持 Chat Completions 和 Responses。
- Codex app-server 作为备用，沿用现有支持，不继续围绕它增加专用功能。

配置分别表达服务商、接口协议、认证方式和模型。选择服务商后提供适用默认值，自定义服务再填写地址等必要信息；模型可获取列表或直接输入。界面只提供实际支持的组合，不把 ChatGPT 连接当作通用 API Key。

不同连接复用相同的任务处理、工具执行和控制逻辑；服务商差异集中在请求适配处。

### 18：模型认证

用户提出的实现方向：ChatGPT 连接使用脚本语言处理，Control Plane 记录 Token 文件位置；目的是将外部协议变化与 Java 主程序隔离，避免协议调整时修改 Java。

已确认的 Python 与 Plane 分工：

- 使用 Python 处理 ChatGPT 登录、凭据导入、刷新及 Token 文件读写，将外部协议细节集中在脚本中。
- Plane 保存连接名称、类型、凭据文件位置与运行设备等必要信息，通过固定的本地调用约定启动脚本、取得状态；Java 不解析外部 Token 文件格式。
- 同一份凭据由统一入口协调刷新，避免多个 Worker 并发刷新旋转令牌；Worker 不各自实现刷新逻辑。
- 文件路径只对所属设备有意义。Plane 与实际调用模型的进程在同一设备时可使用本地文件；另一设备不能直接读取此路径。跨设备共享凭据不纳入当前实现范围。
- 脚本管理文件的安全保存，常规状态输出和日志不回显 Token。具体授权接口与凭据格式在实施前按官方契约核对。

边界说明：仅保存路径不足以完成连接管理；Plane 仍需要知道连接是否可用，并发起登录、刷新或断开等操作。协议实现归 Python，连接记录与用户操作归 Plane。

已确认的异机边界：不与 Plane 运行在同一设备的 Worker，自行管理模型连接与凭据，包括登录、导入、刷新和失效处理。Plane 不向异机 Worker 分发模型凭据，也不要求其读取 Plane 的本地 Token 文件。同机 Worker 可使用 Plane 协调管理的连接。模型运行信息和执行用量仍可按执行记录汇报，汇报不包含凭据。

### 19：模型目录与参数

已确认的规则：

- 自动获取模型列表，也允许手动输入；使用新模型不要求修改代码。
- 模型能力和推理强度按服务商、接口及模型确定，不统一硬套几档；无法确认时使用默认值。
- 每位 Worker 有默认模型和推理强度，任务可以明确覆盖。
- 默认不自动切换模型，避免能力、费用和数据发送目标发生意外变化。
- 可设置允许使用的模型与推理强度范围，让 Worker 根据任务难度选择；每次变化记录原因和实际选择。
- 异机 Worker 自行解析这些设置，并向 Plane 汇报实际使用情况。
- 普通界面显示模型、推理强度；地址和协议细节等放入高级设置，与第 17 项的服务商默认值配合。

### 20：用量与费用

已确认的规则：

- 每次模型调用记录服务商、模型、时间、Token 用量，以及接口实际返回的缓存等细分用量。
- 按调用时适用的价格计算估算费用，可汇总到任务、工作流执行和 Worker。
- 缺少用量或价格时显示“未记录／待计价”，不当作零；有价格后补算。
- ChatGPT 套餐调用单独标明，不把 API 标价当成实际账单。
- 暂不增加复杂的预算审批和额度追加机制，轮数限制继续保留。

价格获取和更新在第 21 项讨论。

### 21：价格更新

已确认的规则：

- Python 脚本获取官方价格，转换成内部统一价格表。
- 程序启动后后台更新一次，此后每日更新一次。
- 保存来源、币种、计价单位和有效时间；支持分时价格。
- 获取失败时保留已有价格并显示更新时间，不阻塞任务。
- 从未获取到价格时留空，后续获取后补算费用。
- 支持人工录入或修正价格。

Java 负责调度脚本、保存价格和计算费用，不解析服务商网页。脚本失效后的修复归第 22 项讨论。

### 22：价格采集失败与修复

已确认：采集失败时报告原因即可，重做或修复由用户决定，不自动重试、不自动创建修复任务。

提供简单操作按钮：

- 重新获取：用户发起一次新的价格采集。
- 修复采集脚本：用户发起普通 Worker 任务，调查失败并修复对应 Python 脚本。

失败时保留已有价格并显示失败原因。失败处理不影响第 21 项已确认的正常每日更新安排；用户主动重做或修复与例行更新分开。

修复候选的运行继续遵循此前明确要求：管理员审阅源码与当前来源页后，明确批准每次运行；使用 Plane 账户权限。复用普通任务、人工确认和执行记录，不新增专用的多层修复流程。

### 23：控制台登录

已确认的规则：

- 仅限本机访问时，默认自动进入，使用本地管理员身份。
- 允许远程访问时，必须登录；不能仅因用户在服务器本机打开页面而将远程开放模式视为本机自动信任模式。
- 首期只保留管理员一种角色，取消操作员、审批员等细分。
- 管理员仍需确认具体危险操作，登录不等于自动批准所有操作。
- 人类登录与 Worker 接入分别处理，不混用凭据。

### 24：Worker 接入

已确认：该项统一称为 Worker 接入，不另设 Agent 成员；秘书连接在秘书部分单独讨论。

已确认的接入规则：

- Plane 在本机启动的 Worker 自动登记和连接，无须手工配对。
- 外部 Worker 使用管理员创建的接入凭据，在所在设备配置后连接。
- 重启重连恢复原成员身份，不重复创建团队成员。
- 停用或撤销接入后阻止后续连接和接单，当前工作是否停止另行确认。
- 接入不逐次要求批准进程启动、能力登记等内部步骤；可执行操作范围归权限部分讨论。
- 异机 Worker 的模型连接仍由其自行管理。

### 25：Worker 权限

已确认的文件访问边界：默认不能访问工作区以外的文件和目录，除非有明确授权，或者用户直接指定。

按用户请求理解具体对象与操作：用户指定某个外部文件，不自动授权访问其整个上级目录；指定读取，不自动授权修改或删除。对已明确指定且含义清楚的操作，不因位于工作区外再次重复申请相同授权。

此前提出的其他权限简化建议仍待确认：成员可用工具、系统和资料构成能力范围，本次任务再明确实际操作对象与范围；Skills 和知识不自动增加权限。取消多层 Owner 绑定、计划托管、接管与归还等用户配置入口，超出范围时提出具体申请。危险操作的具体边界归第 26 项讨论。

### 26：执行限制与危险操作确认

已确认的规则：

- 范围内常规操作自主执行：读取、创建、修改文件，运行任务所需的普通命令。
- 可恢复删除不逐次确认：工作区内文件移入回收区或保留备份，记录删除位置。
- 危险操作需要确认：不可恢复删除、大范围覆盖、破坏环境的命令、发布或向外发送数据。
- 已有明确授权直接执行：不为同一操作重复询问，也不将授权扩大到其他操作。
- 保留轮数和超时限制，触及限制时说明进展，由用户决定是否继续。
- 停止优先：收到停止请求后不再启动新操作，在途操作报告实际停止情况。

确认提示说明准备做什么、影响范围、能否恢复，提供“允许这一次／拒绝”。文件操作同时遵守第 25 项工作区边界。向模型提供本次任务所需上下文和执行已获准的正常联网工具，不因此逐次重新请求相同授权。

### 27：工作记录与可观察性

用户已确认要求：Worker 正在工作的内容需要记录，可以通过界面或 API 观察其状态和工作内容。

建议记录范围，待具体实现设计：

- 当前任务目标、所属工作流执行及当前节点。
- 当前状态、最近动作、更新时间；明确区分运行中、等待用户、等待授权、暂停、失败和已停止。
- 模型调用与工具操作的开始、结束、结果或错误，以及实际生成的阶段结果和交付物引用。
- 用户追加内容的接收与生效位置，控制请求与 Worker 确认情况。

界面与 API 使用同一份真实执行记录，支持查看当前状态及按时间查看过程。工作内容指实际输入、动作、可交付的说明和结果，不要求公开模型内部推理。缺少进度依据时显示当前动作，不编造完成百分比；连接状态与执行状态分开，最后一次记录不等于远端仍在执行。

已确认的成长用途：这些执行信息可用于持续改进 Worker 自身，与第 09 项的成长和经验记录关联。成功结果、失败原因、重试经历、用户纠正和人工决定，都是总结经验的依据。

建议复用同一份执行记录提取有用经验，并保留经验对应的来源；后续任务按需读取。记录不直接全部灌入记忆，不把一次失败或未经核实的模型说明自动当作通用规则。用户仍可查看、纠正和删除经验；修改 Skills、工具权限、模型配置继续遵循已确认的人工确认规则。

已交付安全活动元数据和部分具体失败原因；完整交互、一条完整时间线及日志导出等剩余展示细节仍待确认和完善，真实 API 运行验证未做。

### 28：界面与部署

已确认的规则：

- Plane 以 Web 控制台为主，统一页面、侧栏、弹窗和操作样式。
- 默认展示工作内容，内部 ID、协议和技术参数放入详情或高级设置。
- 保留中、英、日国际化，错误信息和按钮统一翻译。
- 统一状态用语，避免同一种操作在不同页面使用不同名称。
- 同机部署优先简单启动；远程部署提供可照做的配置指引，证书等高级内容单独说明。
- 秘书的桌面形象、托盘和主题留到第 37 项讨论。

不为简化工作另换 UI 框架，也不增加新的部署管理系统。

### 29：秘书对话

已确认的规则：

- 对话作为主要入口，用户直接描述事情，无须先创建任务。
- 简单问答直接回复；需要持续跟踪或执行时，再关联为任务。
- 多轮对话保留上下文，支持附件。
- 处理中可以继续补充内容、纠正方向，也可以暂停或停止。
- 清楚区分“已回答、已提交任务、执行完成”，不把回复结束当作工作完成。
- 关联任务后，可从对话直达执行详情，不在秘书内另做一套工作流管理。

秘书可以独立完成相当一部分工作，不仅是 Plane 的入口；具体边界按第 35 项补充要求理解。交给 Plane 执行时复用统一任务与 Worker 能力。

### 30：记忆与知识

已确认的用途划分：

- 对话历史：保留原始交流，供查看和追溯。
- 个人记忆：用户偏好、长期约定和秘书积累的经验。
- 知识库：系统说明、业务规则、参考资料等可引用内容。

按当前任务读取相关内容，不把全部历史放入上下文。摘要用于压缩上下文，不代替原始记录。记忆支持查看、纠正和删除；知识保留来源。私人内容不自动进入团队共享知识库，确认共享后再提供给其他 Worker。

先做好资料导入、检索和引用，不提前建设复杂的知识管理体系。

### 31：秘书日常工具

已确认的范围：

- 搜索公开信息、读取网页。
- 读取用户提供的附件和授权资料。
- 按用户要求整理、创建和修改文件。
- 查询 Plane 状态、提交任务、跟踪结果。

秘书在自身能力和授权范围内可以独立完成工作，不因需要持续处理就必须交给 Plane；需要团队或其他 Worker 能力时再委派。文件访问与危险操作沿用第 25、26 项统一规则。

普通问答不擅自创建报告或文件；确实需要保存时明确位置，并展示实际保存结果。工具失败直接说明原因；需要授权时提出请求并等待，不一律回答“处理发生异常”。

### 32：工作安排

用户指出 Spring Boot 易于增加周期性任务管理，据此撤回此前“周期性任务暂缓”的建议，将周期安排纳入设计范围。

建议支持马上执行、指定时间执行和周期执行，复用统一任务与工作流执行能力。周期安排保存时区，每次触发产生独立执行记录；修改或停用安排不等同于停止已经开始的执行。

建议先提供每天、每周等直观选项，无须另建完整的调度平台。重复执行重叠策略、停机错过后的处理规则待确认；已开始但中断的执行仍先核对实际结果，不因定时触发而重放。

已确认的调度分工：

- Plane／Spring 管理业务定时安排，包括工作流周期执行和价格更新。
- 安排、时区和下次执行时间保存在数据库；Spring 定期检查到期安排，创建正常执行记录，由现有 Worker 调度领取。
- 重启恢复与防止重复触发依靠数据库执行记录，不把内存定时器视为持久化任务管理。
- 操作系统负责开机启动 Plane、进程异常后重启等进程管理，不逐项注册业务安排。
- 不为此引入额外调度框架或新建独立调度平台。

### 33：秘书运行控制

已确认的规则：

- 停止本次处理：停止当前这件事，保留对话和已有结果。
- 暂停自动处理／恢复：控制秘书是否主动开始后续工作，仍可聊天和查看状态。
- 关闭秘书界面：只关闭界面，不暗示服务或 Plane 任务已经停止。
- 已提交给 Plane 的任务通过统一执行控制停止，不能只停止秘书跟踪就显示任务已停止。
- 中断后先展示最后进展和未确认结果，由用户选择继续或结束，不自动重放可能产生副作用的操作。
- 控制过程记录到执行时间线。

### 34：秘书过程查看

已确认：每次秘书回复旁提供“查看处理过程”，默认保持对话简洁，按需展开。

- 按时间查看模型调用、工具操作、资料来源和结果。
- 可展开查看实际发送给模型、模型返回的内容，隐藏凭据；不要求展示模型内部推理。
- 显示追加内容何时生效，以及等待、授权和停止情况。
- 已委派给 Worker 的工作直接关联统一执行详情。

复用已有记录与展示方式，不另建监控工作台。

### 35：秘书独立工作与 Plane 协作

用户明确的要求：秘书可独立完成相当一部分工作。例如需求澄清可以复用许愿池能力，但不一定提交给 Plane；秘书也可以有轻量定时任务能力。

据此修正此前将秘书主要定位为 Plane 管理入口、持续工作必须交给 Worker 的建议。秘书应能在不连接 Plane 时完成自身能力和授权范围内的工作。

已确认的职责边界：

- 本地完成：需求讨论与整理、查询研究、授权资料和文件处理，以及轻量定时安排。
- 按需协作：用户要求团队执行，或需要完整工作流、其他成员能力时，再提交给 Plane。
- 共用工作方法、Skills 和适用的交互能力，不强制共用 Plane 的任务存储或在线服务；本地工作不自动上传。
- 轻量定时安排由秘书本地进程处理，保存本地安排；Plane／Spring 仍负责已提交给 Plane 的业务安排，不要求为了秘书独立使用而启动 Java 服务。
- 同一安排明确由本地或 Plane 负责，避免两边重复触发；本地服务停机时如何处理错过安排，待统一确认。

此前提出的本机自动登记管理权限、远程认证、最少内容提交和委派后跟踪等连接规则仍待此项具体确认。

### 36：私有数据管理

已确认的规则：

- 对话、记忆、本地工作和安排默认保存在秘书本机。
- 提供简单备份与恢复，备份不包含模型密钥、登录令牌等凭据。
- 普通删除可恢复；永久删除明确提示范围并确认。
- 删除工作记录不自动删除已生成的文件，也不取消已提交给 Plane 的任务。
- 正在执行或结果未确认的工作，先处理清楚再永久删除，避免丢失恢复依据。
- 向 Plane 或知识库共享内容时明确展示共享范围。

保留必要的数据管理，不增加复杂的版本管理和同步系统。

### 37：秘书界面与桌面入口

用户明确的要求：与秘书的会话交流希望更像游戏的操作风格，历史对话内容应方便查看。

建议的交互形式，待确认：

- 主区域突出秘书形象、当前回复和可执行操作，借鉴游戏角色对话框。
- 常见操作提供快捷选项，如继续、补充资料、查看结果、安排时间，同时始终保留自由文字输入，不强制用户只能选择选项。
- 历史入口常驻且一键可达，可选择会话、滚动阅读和搜索；查看历史不要求中断当前工作，返回后保留当前输入与执行状态。
- 当前工作、等待用户处理的问题与实际执行进展可直接查看，状态来自真实记录，不用虚构游戏数值表示进度。
- 沿用现有秘书及 Web Console 的颜色、字体、组件与交互基础，用布局和操作方式表达游戏感，不另建游戏引擎。

此前提出的浏览器与桌面共用界面、本地服务与托盘、可选悬浮人物、主题范围、旧 Tk 移除，以及关闭窗口／退出桌面／停止服务等取舍尚待确认，不因本次风格要求视为全部获准。
