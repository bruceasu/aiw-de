# Agent Factory 与外部 Worker

## 用户入口

`/ui/configurations` 的“专业 Worker 任务配置（高级）”用于手动准备单项任务、组合工作方法和排查准备记录。日常由秘书委派的任务无需再次在此提交。顶部数量卡片仅展示本页可选条件：已配置文件范围的计划、当前执行模型和登记过执行能力的 Worker；登记数量不是在线或兼容数量。

模型和本机 Worker 自动启动统一进入“Agent 工厂设置”，不再跳到“系统”。文件权限入口带入当前所选计划并定位“秘书连接与授权”的文件执行范围；Worker 集群入口明确用于查看已有进程的在线状态。跳转不自动保存表单或修改授权，当前任务进度仍应从关联计划的执行记录核对。

计划详情中的授权入口使用 `/ui/secretary-setup?planId=...`。旧 `/ui/delegation` 链接保留兼容跳转：带计划或秘书选择参数时转到秘书设置，否则转到高级授权页，查询参数原样保留；登录检查继续适用。跳转本身不修改授权。

平台侧边栏 **Agent 工厂设置**（`/ui/agent-factory`）集中保存默认模型、运行时和本机 Worker 自动启动方式。管理员保存一次即可，不必为每项工作编辑 `aidev.ai.profiles`、`aidev.ai.policies` 或手工启动角色脚本。未保存工厂设置时，继续读取原有静态模型目录，保持已有部署兼容。

秘书等待模型设置时提供直达入口，可预填秘书公开的模型名称、Runtime 和推理强度；需要在平台确认保存，不传递 API Key 或登录凭证。工厂设置通过既有平台审计表持久保存，不增加数据库迁移。默认模型选择不赋予计划、文件、命令或预算权限。

## 准备和启动

AgentFactory 执行使用原计划的正式生命周期：`DRAFT → CONFIRMED → COMPLETED`。在当前文件、工具、预算、模型和依赖检查通过后，平台将具体执行说明、仓库、基线及方法确认为原计划的正式步骤，再准备 Worker。原临时分析草案保存为历史快照。秘书确认须使用已有、未过期且次数足够的 A05 代理权限；每次首次确认消费一次，Worker 启动等待和同一执行范围的准备重试不重复消费。没有确认授权时不能自动推进。

正式计划绑定真实的工厂任务，最终状态由已保存的任务报告和实际产物推进；工作区任务还须有真实文件差异与结果提交。阻塞报告、失败或取消不会被记为完成。已完成计划不能通过新准备请求重新执行；需要新的工作时应建立新计划。直接 Worker 执行不代表独立审核已经发生，原有独立审核流程继续适用其自身任务。

V20 迁移保留全部既有计划及引用，增加 `COMPLETED` 约束值和正式方案／任务绑定表，不自动认领或重跑历史任务。SQLite 在单个事务中复制计划表并检查外键，PostgreSQL 调整状态约束；上线前保留数据库备份。旧程序不认识新状态，回退时需停止服务并使用迁移前数据库备份，不能覆盖运行中产生的新记录。

历史修复通过本人会话的 `POST /api/r1/authority/execution-configurations/reconcile-plan`，指定 `planId`、已有成功 `taskId`、`expectedPlanVersion` 和 `reason`。平台核对原准备、账号、真实结果及无待执行任务后，确认原计划并记录完成；此操作不创建任务、不调用模型，不修改历史任务或冒充独立审核。

1. 使用原计划、不可变基线、方法和请求标识生成准备记录。
2. 优先复用心跳有效、具备相应仓库和配置适配器的在线 Worker，包括外部实现。
3. 没有兼容 Worker 时，先核对执行政策、工具范围、预算和依赖，然后在数据库事务提交后启动随平台安装的 `workers/process-python/managed_worker.py`。启动命令为固定参数数组，不经过 shell。凭证仅通过子进程环境传递。
4. 本机 Worker 通过普通协议注册和提交能力元数据。启动前不伪造在线状态，也不把准备记录标记为正式任务。
5. 秘书收到 `WORKER_STARTING` 后跟进原请求，通过 `POST /api/r1/authority/professional-tasks/{id}/continue` 继续同一份准备记录。每次重新核对当前身份、托管、基线和政策；正式任务只有一个确定标识。GET 回执和诊断不负责启动进程或重试准备。

启动按仓库、Runtime 和工厂设置版本去重。单个启动等待兼容登记最多约 120 秒，失败不无限拉起。默认最多管理 4 个本机进程，可通过 `aidev.agent-factory.max-workers` 调整；数量限制不会停止外部 Worker。源码安装目录不同可配置 `aidev.agent-factory.worker-root`。进程状态页只展示固定错误码和说明，不输出异常原文、凭证或模型响应。

平台关闭时仅停止自身创建和跟踪的进程树；活动任务仍遵守平台租约与恢复规则，不将中断当作成功。外部 Worker 的启动、更新、停止继续归外部宿主管理。平台重启后先根据注册信息和心跳复用尚在线的兼容 Worker，不根据旧 PID 终止未知进程。

## 本机环境边界

工厂不会安装 Python 包、Codex 或 Git，不会登录账号或复制秘书凭证。Python 可从 PATH 查找，也可在高级设置中指定已安装解释器。

- 工厂托管的 Codex Worker 默认使用 `host-actions`：复用现有 CLI 登录，通过与秘书相同的纯模型通道返回 JSON 工具请求，由平台受控 Broker 执行文件与 Git 操作。原生 Shell、浏览器、插件、多 Agent 等工具关闭并核对其生效状态；模型进程不获得工作区写权限。无需第二次登录或手动配置专用目录。显式指定 `AIW_CODEX_GUARD_HOME` 时保留原动态工具模式及其独立受控配置要求。
- OpenAI Agents SDK 使用平台进程已有的 `OPENAI_API_KEY` 等运行环境。API Key 不保存在工厂设置表单或审计记录。
- 自动 Worker 不启用命令适配器。需要命令工具的方法仍需显式命令政策以及兼容的外部/预配置 Worker。
- Windows Codex Worker 能力登记接受 `win32`，沿用现有 Windows App Server 进程管理；这不代表任意已安装 CLI 版本通过协议和受控配置检查。

启动错误会显示缺少依赖、找不到程序、受控目录未就绪或具体初始化错误码。修复环境后保存工厂设置并重新准备受阻任务；已受理或结果未知的任务仍只核对原回执。

受控读取接口的 `offset` 是从 1 开始的行号，`limit` 为 1–500 行；Skill 文件仍按从 0 开始的字节偏移读取。可纠正的读取参数错误会返回给模型，尚未确认的写入与租约异常仍立即停止。实现角色不能仅靠非空报告认定成功：明确报告阻塞/未实施，或相对基线没有文件变更时，返回待处理结果。秘书也会拒绝将历史回执中明确声明未实施的报告显示为完成。

## 外部实现继续接入

外部 Worker 无须继承 Java 工厂类，也无须接受平台进程管理，继续使用现有 Worker Token 和 Worker Protocol v1：

| 环节 | 接口 |
| --- | --- |
| 注册 | `POST /api/r1/worker-protocol/v1/workers/register` |
| 能力登记（工厂任务需要） | `POST /api/r1/worker-protocol/v1/workers/{worker}/configuration` |
| 领取任务 | `POST /api/r1/worker-protocol/v1/tasks/claim` |

心跳、开始、完成、失败、停止及结果报告继续使用原协议。普通任务按原能力匹配；工厂生成的任务额外要求 `execution-config-v1`、`execution-guard-v1`、`skill-files-v1`、精确仓库能力及对应的配置/守卫协议元数据。Worker 必须消费固定配置、遵守租约和工具范围，并提交真实执行结果，不能只声明能力而省略适配器实现。

当前工厂模型支持 `codex-app-server` 与 `openai-agents`。外部实现可以使用其他语言，但执行这类工厂任务仍需实现它声明的 Runtime 与配置契约。其他已有任务和 Worker 不会因启用工厂被替换或自动停止。

## 验证范围

代码只进行离线生产编译及静态检查。没有自动运行模型、启动真实 Worker、安装依赖或验证 Windows/Unix 的完整运行流程。编译通过不代表本机登录、CLI 协议、子进程关闭和外部 Worker 互操作已经通过运行验证。
