# aiw 能力复用评估

- 评估日期：2026-10-04
- 主系统：AI Worker
- 能力来源：同级 aiw 仓库
- 评估方式：当前本地源码与文档的静态检查
- 状态：能力选型报告，未实施接入或源码迁移

Worker 公共执行基础、角色政策及 pi 机制的整体融合另见 [Worker 融合计划](worker-pi-integration-plan.md)。

## 1. 结论与原则

aiw 的部分算法、校验逻辑和 CLI 工具适合复用到 AI Worker。建议优先迁移需求完整性检查、来源引用校验和结构化工程证据校验，同时选择少量 CLI 查询能力接入 Worker。

复用单位是具体能力，不要求整体整合 aiw。适合独立迁移的逻辑按 AI Worker 的架构和模型实现；已有命令能够完整解决问题时，通过受控适配器调用 CLI。

统一遵守以下边界：

1. AI Worker 主导任务状态、依赖、调度、租约、审批和验收。
2. 迁移的逻辑适配 AI Worker 的模块、数据模型和约定，并记录来源。
3. CLI 的调用时机、参数、权限和结果处理由 AI Worker 决定。
4. aiw 输出作为结果或证据，由 AI Worker 校验后使用。
5. 每项状态和工作区资源只设一个管理者，避免两套机制同时修改。

## 2. 当前实现基线

### AI Worker

AI Worker 是 Java 控制平面，通过 Worker Protocol 管理外部 Worker。已有能力包括：

- 任务和依赖图、Worker 能力与容量管理。
- 执行尝试、租约、心跳和过期恢复。
- 需求分析、架构、规划、并行实现及集成。
- 审查、验证、修复循环、工程门禁和人工审批。
- 知识文档、内容摘要及上游关联。
- Worker 的 Git 工作区创建、结果提交、可选发布及清理。

### aiw

aiw 是支持插件扩展的工作流 CLI，包含 Issue、FD、Skills 及辅助工具。当前 CLI 入口内建部分命令，其他命令通过插件分发，`issue` 转发给 `req` 插件。

能力评估应覆盖三类实现：CLI 内建能力、当前仓库附带插件，以及安装环境中另行分发或扩展的插件。没有内建处理器不代表没有该能力；调用 `aiw <command>` 时，该命令可能由插件提供。本报告主要覆盖前两类，尚未盘点实际安装环境中的完整插件目录。

主要 Go 代码位于 `internal/`，不能由其他 Go 模块直接导入；Java 控制平面也不能直接导入 Go 包。源码复用需要提取共享包或迁移为对应语言实现，CLI 调用则可以跨语言使用。

相关依据：[CLI 入口](../../aiw/cmd/aiw/main.go)、[模块定义](../../aiw/go.mod)。

## 3. 值得迁移的逻辑

| 能力 | 当前 aiw 实现 | AI Worker 的收益与落点 | 建议优先级 |
|---|---|---|---|
| 需求完整性检查 | 检查角色、问题、工作流、目标、范围、规则、异常、数据、权限、依赖和验收等维度；识别未决项与冲突 | 增强需求分析输出校验，为后续架构任务提供缺口清单 | 高 |
| 结论与来源绑定 | 通过来源、摘要和原文引用，校验需求 ID、版本及人工确认信息 | 防止旧材料和无依据结论进入后续设计 | 高 |
| 结构化工程证据校验 | Markdown 与同名 JSON 交叉引用；校验 schema、类型、FD、来源事件及重复 JSON 字段 | 增强执行报告校验，绑定 task、attempt 和结果版本 | 高 |
| 进程树生命周期管理 | Windows Job Object 及其他平台的进程管理逻辑 | 增强 Worker 在取消或租约丢失后的子进程清理 | 高，需专项验证 |
| Skills 包完整性与发布 | 目录校验、符号链接限制、包摘要、暂存校验、发布和管理清单 | 支持 Worker Skill 包的完整性检查和来源追踪 | 中高 |
| 上下文快照组织 | 区分材料加载状态、实际摘要、候选结论与确认信息 | 增强需求、架构、规划之间的交接与输入复现 | 中高 |
| 路径边界检查 | 路径规范化、符号链接解析、允许目录检查 | 用于工具输入、报告路径及文件访问校验 | 中 |

### 3.1 需求分析校验

可参考：

- [readiness.go](../../aiw/internal/issue/readiness.go)
- [coverage.go](../../aiw/internal/issue/coverage.go)
- [context.go](../../aiw/internal/issue/context.go)

这些实现将模型建议、材料加载和可信确认分开处理。引用校验包括输入版本绑定，适合提取为确定性的需求分析校验组件。

迁移时保留检查算法，调整 Issue 身份、版本、来源和确认信息的映射。aiw 的确认策略不能直接替代 AI Worker 的审批政策。结构有效也不等于业务完整或已获批准。

### 3.2 工程证据校验

可参考 [aiw-fd.py](../../aiw/plugins/aiw-fd.py) 中的 `structured_evidence`、测试报告与授权记录校验函数。

值得吸收的是人可读报告与机器字段的对应关系，以及证据对来源和版本的绑定。应映射到 AI Worker 的任务、执行尝试、上游结果和代码版本，增强现有报告与门禁机制。

不直接迁入 FD 的角色路由和生命周期。报告格式或协议变更需要明确兼容策略。

### 3.3 进程管理

可参考 [Windows 进程管理](../../aiw/internal/ai/managed_process_windows.go) 及同目录的其他平台实现。

现有 Go Worker 使用 `exec.CommandContext` 调用执行器，可以借鉴进程树管理逻辑。当前静态检查不足以证明所有平台的后代进程都能正确退出；迁移前后需要检查完整调用链，并专项验证正常完成、取消、租约丢失与异常启动路径。

### 3.4 Skills 与路径处理

可参考：

- [Skills 实现](../../aiw/plugins/aiw-skills/aiw-skills.py)
- [路径读取政策](../../aiw/internal/commands/ask/path_policy.go)

提取完整性和路径校验算法，按 Worker 的目录、信任范围和运行方式适配。aiw 的交互确认、用户级目录及发布重试策略不宜直接照搬。路径检查也不能单独视为运行隔离保证。

## 5. 暂不整套接入的能力

| 能力 | 原因与处理方式 |
|---|---|
| FD 的 claim、emit、resume、close 和角色路由 | 与 AI Worker 的任务和管理机制重叠；吸收证据设计，不建立第二套调度与审批 |
| 本地 Task / Session 生命周期与存储 | AI Worker 已有数据库、执行尝试和租约；整体迁移收益低 |
| worktree 创建、提交、发布和清理 | Worker 已有实现；仅吸收有价值的校验或恢复逻辑，资源必须由唯一管理者维护 |
| 插件自动发现 | 可参考跨语言启动方式；服务环境使用固定工具清单和路径，避免由工作目录或 PATH 自动选择程序 |
| 交互式 ask、Commit 向导和项目初始化 | 更适合人工操作或开发环境准备，当前自动 Worker 流程的收益有限 |
| Gateway 替换编码执行器 | 当前网关定位与执行约束不同，暂不作为编码执行器替代方案 |

当前 Gateway 文档描述独立空工作目录、只读和禁用执行工具的配置，其函数工具调用也由调用方执行。是否适合作为分析后端应另行评估，不能据此推断具备现有 Worker 的仓库修改能力。依据：[Gateway README](../../aiw/program/agent-gateway/README.md)。

### 命令入口不确定性

aiw README 列出 `aiw context`、`aiw wt` 等命令，但本次检查的当前内建入口及仓库插件目录未找到对应实现。CLI 入口明确将 `wt` 留给外部插件处理。因此，这些能力属于插件实现及分发情况待核实，不能因为缺少内建处理器或仓库内文件就判断 aiw 不支持。

接入时应盘点实际分发版本和插件清单，并确认插件来源、依赖与命令契约。确认后的插件能力与内建能力一样可以成为 AI Worker 的工具候选；其取舍仍由收益和管理边界决定。

### 插件复用方式

优先通过 `aiw <command>` 调用已有插件，复用 aiw 的分发和解释器选择。若部署需要固定单个插件，也可考虑直接调用插件入口，但需核对其对 aiw 注入环境和启动上下文的依赖。

每项工具登记应同时记录 aiw 版本、实际插件入口、插件版本或内容摘要、解释器与依赖、输入输出契约，以及读写和网络需求。aiw 版本本身不足以确定外部分发插件的行为。

AI Worker 还可以按需提供自己的插件，复用 aiw 的命令入口。此类插件执行指定能力或通过既有 API 请求控制平面，由 AI Worker 继续管理任务和审批；本次尚未设计或实施该扩展。

## 6. 工具接入边界

建议的调用关系：

```text
AI Worker 控制平面
  -> Worker 领取任务并维护租约
     -> 工具适配器
        -> aiw CLI 或指定插件
     -> Worker 回报结果和证据
  -> 控制平面校验、验收和审批
```

工具适配器是建议新增的组件，不是已实现功能。其接口应当：

- 按具体能力和子命令开放，固定可执行文件、插件来源和工作目录。
- 使用参数数组传递输入，避免拼接 shell 命令。
- 分开处理 stdout、stderr、退出码和结构化输出。
- 逐命令确认非交互行为、JSON 格式及失败语义，不假设所有命令支持 JSON。
- 关联 task、attempt、工具版本、耗时和结果，敏感输入按政策处理。
- 将取消和租约丢失传播到工具进程，设置输出与执行时间边界。
- 由 AI Worker 决定外部写入和高风险操作的权限，不用插件元数据代替授权。

aiw 的插件入口默认继承环境和标准输入输出，部分调用路径缺少所需的有界输出或取消接口。相关实现可参考，但不能原样作为服务端工具适配器。依据：[插件执行](../../aiw/internal/plugin/exec.go)、[插件发现](../../aiw/internal/plugin/discover.go)。

## 7. 建议实施顺序

1. 迁移需求完整性与来源引用校验，增强需求分析输出。
2. 迁移结构化证据校验，增强报告对 task、attempt 和 revision 的绑定。
3. 接入少量 CLI 查询工具，优先 Skills 和 GitHub。
4. 专项增强 Worker 进程树取消，验证正常结束、取消和租约丢失路径。
5. 在明确需求后接入 Skills 安装、代码索引和外部交付写入。

每项实施前核对近邻代码、当前契约和来源。协议、持久化、权限、依赖、并发或取消语义发生变化时，先明确风险和兼容范围。

## 8. 验证范围与剩余风险

本次评估实际使用 `Get-Content`、`Get-ChildItem` 和 `rg` 读取源码与文档，没有运行 aiw CLI、测试、编译、构建、格式化或网络调用，也没有实施迁移。

剩余风险包括：

- 实际安装版本与仓库源码的插件完整性可能不同。
- 命令的机器输出、非交互行为和失败语义尚未运行验证。
- 进程树取消和跨平台执行效果尚未验证。
- Skills 目录、代码索引存储与多 Worker 隔离需要具体设计。
- 迁移可能触及输出契约、权限或依赖，不能默认扩大范围。
- 源码迁移前需核对来源和适用许可；本次未完成许可审查。

选定实施范围后，可另行授权与该能力对应的最小验证：CLI 输出与失败契约、进程树取消、证据版本不匹配拒绝路径，以及索引对当前结果版本的适用性。该报告不授权执行这些检查。
