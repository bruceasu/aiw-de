## 问题与使用者

多个角色处理同类执行问题：租约、期限、工作区、上下文、工具权限、并行、副作用、输出限制、结果校验和证据。若各自独立实现，容易出现行为不一致、重复维护以及角色语义与执行机制耦合。

当前整体计划指出 API Worker 的收尾 Git 操作未纳入同一任务取消信号，工具反馈主要为文本，Skill 参考材料与上游报告整体展开，其他运行时也有相似角色处理。这些是静态发现；取消竞争、SDK 行为、性能和成本尚未得到运行证据。

| 使用者 | 需要解决的场景 |
|---|---|
| Worker 维护者 | 一处修复公共执行逻辑后，各角色获得一致行为；角色差异清楚且可维护 |
| 操作者 | 在取消、超时、租约丢失或执行失败时，知道哪些操作结束、哪些副作用已发生以及如何恢复 |
| 审查与验收者 | 判断结果对应哪个 task、attempt 和代码版本，区分实际执行证据与模型陈述 |
| 需求与架构角色 | 在有限上下文内获取可信来源、约束、上游结论和待确认信息 |

## 目标与成功标准

1. 各现有可执行过程角色共享可靠的执行基础，角色差异通过能力政策、Skill、上下文重点和报告要求表达。
2. 从工作区准备到结果发布统一处理取消与期限，清理前等待活动操作结束，过期结果不能被接受。
3. 允许独立工具并行，对冲突资源与副作用提供明确协调，而不是全部串行。
4. 工具反馈有界、可理解、可关联；最终报告不能掩盖关键工具失败或证据缺失。
5. 输入来源、Skill 版本、上下文预算和压缩可追溯，保留关键约束和工具调用对应关系。
6. pi 的机制和 aiw 的能力服务于 aiw-dev 的任务体系，兼容现有部署与运行时差异。

以上成功标准对应整体计划的“公共职责与管理边界”“并行工具与副作用”“上下文和预算”“验收场景与证据”。效率与成本目标通过同任务前后数据比较，不承诺未经测量的改善百分比。

本 Issue 保留整个 Worker 公共基础建设范围，不把整体工作拆成互不关联的重复需求。后续可以按依赖分阶段交付 FD，每次交接记录其覆盖的结果，阶段完成不能代表整个 Issue 完成。

| 二 公共执行基础 | 生命周期、工作区、工具执行、资源协调、截断和编辑反馈 | 核心需求范围；模块拆分由 FD 决定 |

角色覆盖 Requirements、Architect、Planner、Coder、Integrator、Reviewer、Verifier、Integration Verifier 和 Repairer。Release Readiness 与 Orchestrator 目前缺少可执行 TaskType，保留其现状；新增可执行角色需要独立评估。

旧 codex-* 示例的维护定位需要盘点。demo-deployer 的部署权限和发布保证不纳入默认公共能力开放。

## 非目标

- 不建设第二套任务调度、租约、审批或验收系统。
- 不复刻 pi 的交互界面、会话树或自由模型切换。
- 不默认整体替换 Agents SDK，也不默认引入多 Provider 重构。
- 不把 aiw 的 FD 管理状态作为控制平面的任务状态。
- 不自动升级依赖、修改数据库、Worker Protocol、公开 API 或新增 verdict。
- 不因为工具或角色存在就授权测试、网络、安装、推送、部署或外部消息。

## 验收示例

1. 同一公共执行基础用于 Reviewer 和 Coder；Reviewer 的写入请求被拒绝，Coder 可在指定工作区执行已授权编辑。
2. 独立读取或不同文件操作可以并行；同文件两个编辑不会因并发读改写丢失更新；先前操作失败后后续操作可结束。
3. 模型执行、工具或 Git 收尾期间租约丢失时，记录取消与已发生副作用，不回报有效完成；清理不早于活动操作终止。
4. 超长 shell 输出仍能提供末尾错误及明确截断标记；搜索未完成时不能报告为完整搜索；JSON 超限时保持结构或明确拒绝。
5. 多区域编辑有重复或重叠匹配时，不产生部分计划修改；BOM、换行及外部内容变化按明示政策处理。
6. 首轮上下文超限或历史压缩时，保留关键规则、验收及调用对应关系；模型摘要可回查原始来源。
7. 工具失败、只读工作区变脏、缺少 verdict、证据保存失败和完整性不足都按明示规则处理，不能仅凭模型声称 done 通过验收。
8. 缺失插件、错误版本、非法输出或无网络授权时，报告具体错误；插件输出不能自行批准任务或外部写入。
9. 旧 Profile、规划 manifest 和报告仍按现有契约使用；其他运行时缺少某能力时明确表示，而不是伪造证据。

示例来自整体计划“验收场景与证据”。这些是目标场景，不是已执行结果，也不授权自动运行检查。

## 假设与工程建议

首期以 process-typescript-with-api 为落点并保留 Agents SDK，是来源计划中的建议；用户已指定该 Worker 作为参考对象，但未单独批准每项模块设计或跨语言迁移批次。

公共库是否提取、内部模块名称、工具调度实现、摘要策略、SDK 钩子和具体测试方案可推迟到 FD 设计。原因是需要近邻源码与实际 SDK 支持矩阵，这些选择不改变当前总体目标。

自动摘要可以作为有界、可关闭能力设计；预算和明确失败处理仍需成立。Verifier 受控执行和新角色启用属于后续政策变更，不能仅作为工程细节绕过决策。
