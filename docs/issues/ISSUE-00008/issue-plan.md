## 1. 使用者、问题与目标

当前面向单机使用的个人用户。用户希望通过 Chat 与秘书 Worker 讨论工作意图，由秘书安排当前支持的专业工作、按约定时间入队、查询进度、跟踪结果，并向用户反馈。等待工作到期或执行期间，用户仍能继续与秘书讨论其他事项。

目标成果是：用户可以把澄清后的工作交给秘书安排，并能持续掌握工作内容、安排时间、执行状态、结果和需要人工处理的事项。秘书不得把聊天承诺当成已保存的安排，不得编造任务状态或默认获得用户的全部操作权限。

“部署 Worker”只是专业工作示例。Jenkins、AWS、特定应用部署、健康检查等不是本 Issue 必须交付的固定业务集成；能安排的工作以平台真实能力、适用 Worker 和当前有效授权为准。

## 2. 用户已确认的规则

### 2.1 产品与职责

4. 以当前架构和实现为准。旧 Handoff 的 R9 冻结基线及过时版本描述不能约束或替换当前系统。

### 2.2 单机优先与未来演进

1. 当前以单机为主，从现在开始标记数据归属，避免日后提供多用户时大范围返工。
2. 工作区、完整所有权及共享模型尚未全部确定；磁盘/代码工作区不自动等于用户隔离边界。
3. 资料分享到公共知识库、项目移交、Worker 归属、雇佣他人 Worker 与公共 Worker 均为未来方向，目前不交付多用户协作、商业市场、支付计费或完整租户运营。

### 2.3 时间安排与变化

1. 首期时间精度到分钟，参考 crontab 的简单做法；允许正常秒级偏差，不新增逐安排的延迟容忍配置。
2. 指定时间表示到期进入执行队列，不承诺此刻实际开始或完成。已入队后等待 Worker 不属于错过调度。
3. 系统停机/休眠等原因真正错过安排时间后，必须重新确认，不默认恢复后补跑。
4. 安排后工作内容有变化，需要确认是否执行最新内容；不自动切换到最新内容，也不凭旧确认默默执行改变后的工作。
5. 取消须区分待触发、已排队、执行中及已产生副作用；取消申请不等于已停止或已回滚。
6. 外部请求已发出但结果未知时，先核实结果或转人工，不盲目重试可能重复产生副作用的动作。

分钟粒度的整理理解：安排在 15:00 的工作于 15:00:30 入队属于正常触发；停机错过目标分钟并在 18:00 恢复则需重新确认。此例说明本产品需求，不声称所有 cron 实现都提供相同保证，也不表示已选定 OS crontab。

### 2.4 完成与核验

1. 开发计划保留现有独立 Worker 评审。

3. 核验与重做业务动作分开，防止“评审返工”导致重复外部操作。需要何种证据由各工作能力明确，模型自述不自动等于充分证据。

## 5. 验收例（需求期示例，未运行）

1. 用户讨论一个通用工作请求，秘书对关键缺失信息继续澄清；安排成功后返回可查询的真实标识，保存失败时不声称安排成功。
2. 15:00 的安排以分钟粒度到期入队；无 Worker 时明确显示排队，与已开始和已完成区分。
3. 停机错过安排后保留原记录并请求重新确认，未确认前不执行。
4. 相关工作内容变化时展示变化和拟执行内容，需要确认是否采用最新内容；重复确认不产生重复有效委派。
5. 取消待触发安排后，旧事件不会重新启动该安排；对已领取或外部操作中的任务，显示真实的停止/结果核实状态及能力限制。
6. 外部操作响应丢失时先核实结果或转人工，不把未知结果直接当成可安全重试的失败。
7. 开发工作经过既有独立评审；普通事务按对应类型的证据核验，核验失败不默认再次产生外部副作用。
8. 到期时授权已撤销、到期或额度耗尽，不能凭早先安排继续动作；关联代理批准时保持真实身份与独立性。
9. 新增对话、安排、任务及相关资料保留明确归属和参与者线索；不把它冒充已完成的多用户隔离或历史所有权迁移。
10. 任务执行结果与通知状态可区分，通知失败不会触发工作重做；分析不可用时如实呈现原始失败及证据限制。
11. 秘书与需求处理 Worker 即使共享 Chat 基础能力，也不会串用业务上下文或自动继承代理权限。
