## 使用者、问题与目标

用户通过秘书提交目标、参加需求讨论、跟踪工作、回答专业问题和收取结果，无需持续停留控制台。用户仍可在控制台查看细节、审阅和直接操作；正式状态与权限由平台管理。

## 范围与规则

1. 秘书为主要联系人，Telegram 与聊天界面作为交互渠道。首期接入个人秘书聊天、Telegram 私聊与 Web Console；私人数据仅按办理工作所需提交平台。
2. 保留需求讨论和需求分析专业职责；秘书组织或转交交流，无须额外改写每条专业回复。
3. 计划 ask 与执行 Agent 临时问题统一关联具体工作，保留原问题、必要上下文、选项、用户原始回答及处理状态；整理展示不得改变专业原意。
4. 不同渠道操作同一问题，避免重复消费或关联错工作；批准与拒绝绑定具体请求及范围，一句“可以”不能变成一般授权。
5. Agent 提交澄清或确认请求后可等待并释放执行槽；回答作为输入恢复对应工作，不依赖原模型会话存活。
6. 展示进展、成果、问题及关键分支，不展示模型内部推理。允许用户暂停、终止与回答。
7. 暂停阻止新派发或推进并显示在途情况；中断当前执行使用取消机制。终止阻止后续工作，Worker 确认前不能显示已停止；终止不自动回滚已发生外部操作。

## 已确认：循环到限申请与秘书审批（2026-10-22）

来源：用户确认循环暂固定为 3 次回跳，初始执行另计、共最多 4 轮；到限向用户申请授权，秘书在获授审批权限时可按 policy 处理。

- [ISSUE-00010](../ISSUE-00010/issue-plan.md) 产生具体工作的追加申请；本 Issue 负责经秘书展示到限原因、已消耗次数、申请范围和待决定内容，保留用户或代理的真实回答与身份。
- 用户为授权决定者。秘书只有在有效委托明确覆盖本次审批、且满足适用 policy 时，才能代用户处理；秘书在线或能转交问题本身不等于有审批权限。
- 没有相应授权、超出 policy 或无法判断时，请求继续交用户处理，保持待处理，不因等待超时或普通聊天答复而默认批准。涉及正式授权生效的约束由 [ISSUE-00013](../ISSUE-00013/issue-plan.md) 拥有。
- 审批决定必须关联同一申请，重复回答不能重复增加额度或恢复执行。追加量与范围由每次申请和决定明确，policy 由实际委托配置提供；本次需求确认不实际启用秘书代理权限。

验收例：到限后无委托的秘书仅通知用户；有适用审批授权和满足 policy 的秘书可提交代理决定；无论经哪个渠道处理，同一申请只产生一次有效追加。循环计数及获批续行的验收归属 ISSUE-00010。

## 已确认：首期问答渠道、暂停与新库（2026-10-22）

用户同意最近建议，首期接入个人秘书聊天、Telegram 私聊和 Web Console，作为同一正式问题的三个入口。Telegram 绑定明确用户和聊天，群聊、多用户代答及其他渠道不在首期承诺内；技术绑定方式留给设计。

- 默认暂停阻止新工作及后续推进，让在途任务按已有授权收尾；界面如实展示仍在执行的工作。结果、回答和确认继续留存，暂停中不自动恢复或推进。
- 中断当前执行通过单独取消请求处理；未取得 Worker 停止确认时显示等待确认，失联或结果未知时保留未知，不能误显示已停止。终止不自动回滚外部操作。
- 回跳额度按同一计划内同一业务循环累计，每次追加申请明确增加次数及范围；秘书仅按有效委托和 policy 代批，否则由用户处理。具体 policy 由用户实际配置，未有委托不默认获得审批权。
- 新部署不迁移旧运行数据库；用户自行删除旧 DB，本轮不实际删除。新库中的问题、回答、审批和去重记录仍须持久化，私人数据仍只按办理工作所需提交平台。

验收补充：同一问题经三个入口处理不会重复推进；暂停期间收到回答或完成结果不会启动后继；取消待确认不能显示已停止。此为后续目标，未运行验证。
