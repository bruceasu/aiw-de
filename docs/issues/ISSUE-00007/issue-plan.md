- 日期：2026-10-18。

- 建档依据：用户明确要求“先生成 issue 吧”。
- 请求者与业务决策者：当前会话用户。
- 整理方式：issue-management 主持需求澄清，采用 intake 视角，结合 grill-with-docs 检查关键边界。
- 准备度：INCOMPLETE。已确认目标澄清先于计划、“转正”产出适合 Worker 理解的正式目标、可选创建计划草案及自动分析 Steps；目标就绪判断和未完成计划的恢复等边界仍待明确。

## 用户明确提出的需求

1. UI 提供入口，让用户与 AI 聊天、讨论目标草案；由独立 AI Worker 对接。
2. 管理多个目标草案，支持创建、更新、删除、转正式；转正式可以附加生成计划。
3. UI 应美观，具有科幻和游戏风格。
4. Worker 具备 AIW issue-management、Planner/Design 等相关 Skills，可使用项目知识及其他知识库；可使用 AIW research、代码 MAP 分析，以及 rg、AIW 插件、tree-sitter 等技能和工具。
5. Worker 可使用 Codex 或 OpenAI Agent SDK / OpenAI API，默认采用 OpenAI Agent SDK / OpenAI API。
6. 目标草案是计划的前置工作。用户可能只有泛泛的自然语言描述，缺乏必要信息；先通过讨论澄清，不让 Worker 猜测关键需求。
7. “转正”不创建 AIW Issue，而是参考 issue-management 生成 issue plan 的整理方式，产出更适合 AI Worker 理解和使用的目标内容。它不是编号 FD，也不等于创建或启动运行计划。
8. 转正可附带可选交接操作：使用已整理的目标内容，创建一个新的计划草案；AI Steps 分析可用时触发分析，自动补全计划草案。如果不能自动完成，则停留在编辑页面，让用户补充 Steps 等内容。

9. Chat 需允许用户提供文件，帮助负责目标澄清的 Worker 理解需求。用户提出常见文本（TXT、MD、HTML、源代码等）、Word 文档、图片、XLS/XLSX、PDF；其中“docs”是否指旧版 .doc 尚待明确。用户最初提出 MarkItDown 并要求检查商业许可，后续已明确由 AIW 封装，见第 10 项；Chat 不直接引入该依赖。

10. 用户将把 MarkItDown 整合进 AIW，由 aiw file-convert 统一提供文件转换为文本的功能，具体命令参数后续明确。Chat/Worker 将其作为文件转文本能力的集成边界，不直接集成 MarkItDown；命令整合由用户另行推进，本次不实现或调用该命令。

第 6–8 项由用户此前明确澄清；第 9–10 项为附件需求及已确认的转换能力边界。用户提出参考 handoff / issue plan 的产物质量及交接方式，不表示把 AIW Issue 生命周期搬进运行时目标管理。

这些是产品能力要求，不是授权本次会话运行模型、分析整个工作区、访问外部知识库或执行工程实现。

## 问题与目标

已知使用者是准备创建计划、但最初可能缺乏清晰目标及必要信息的用户。期望路径为：进入工作台 → 创建或选择目标草案 → 与独立 Worker 讨论并利用项目证据补足信息 → 更新草案 → 产出适合 Worker 理解的正式目标 → 可选创建新的计划草案 → AI Steps 可用时自动分析并补全，不可完成时由用户继续补充。

已确认的问题是自然语言目标可能含糊或缺少必要信息，直接进入计划会迫使 Worker 猜测。用户需要先谈清楚，再把整理后的目标交给后续计划。用户目前的具体替代方式、使用频率及多人协作要求尚未提供。

业务成果是“从模糊意图到可供 Worker 使用的明确目标，再按需进入计划草案”，并保留多个目标的讨论和管理能力。

## 已确认的概念与交接

- 目标草案：计划前的讨论和澄清载体，允许信息尚不完整。
- 正式目标：参考 issue plan 整理质量形成的 Worker 可理解目标内容；不是 AIW Issue。其存储形式及是否独立于草案建实体属于后续设计问题，不预定表结构。
- 计划草案：可选的下游产物，使用正式目标创建；可以自动分析 Steps，也允许人工补充。
- “自动完成计划草案”指补全草案内容，不等于启动执行或把业务计划标记为完成；这是根据用户明确使用“草案”作出的解释，未获得自动执行授权。
- 正式目标建议包含目的、背景、范围与非目标、约束、预期产出、可判断的完成条件、已确认决定、证据和未决事项；这些字段是待确认建议，不能将聊天摘要直接冒充已充分澄清的目标。
- 目标内容足以转正的就绪标准、关键缺失是否阻止转正、以及哪些未决项可交给计划阶段继续澄清，仍待确认。

## 已确认的文件转换边界（2026-10-18）

- 文件转文本统一由 aiw file-convert 提供，MarkItDown 封装在 AIW 内；Chat 不直接依赖其 Python API、可选依赖或插件。
- 用户负责另行推进 AIW 内的命令整合；本需求负责附件的目标关联、使用转换能力、展示结果及为 Worker 提供上下文，不重复交付转换引擎。
- 当前仅确认命令名称及“转换为文本”的用途；参数、输入输出、错误与部分成功表达、支持格式、版本约束和部署位置均未约定，也未核实命令已存在或可用。
- 后续基于已明确的命令契约接入，不预先编造选项、输出结构或替代命令。若契约尚未就绪，记录集成依赖；目标聊天、内容整理和 UI 需求仍可继续澄清。
- 文本转换与图片、扫描件及复杂图表的视觉理解分别评估。不能由“file-convert”名称推导已支持 OCR、视觉模型或云服务。
- 以下 MarkItDown 调查保留为 AIW 封装的选型依据，不再将直接集成 MarkItDown 作为 Chat 的待选实现方案。商用许可及实际依赖核对仍由转换能力的交付保留证据。

- [DOCX 转换器](https://github.com/microsoft/markitdown/blob/main/packages/markitdown/src/markitdown/converters/_docx_converter.py)：已核实其接收 .docx；不能据此承诺旧版 .doc 原生支持。

- [PDF 转换器](https://github.com/microsoft/markitdown/blob/main/packages/markitdown/src/markitdown/converters/_pdf_converter.py)及 README：内置方案提取文字/表格；扫描件和嵌入图片需要另行考虑 OCR、视觉或云转换路径，不能保证基础转换覆盖。
- [依赖配置](https://github.com/microsoft/markitdown/blob/main/packages/markitdown/pyproject.toml)：DOCX、XLS、XLSX、PDF 有独立可选依赖；引入时应按所需格式确定依赖集合，而非默认启用所有能力。所读取的是 main 分支快照，不是已经选定的发布版本。
- [官方安全说明](https://github.com/microsoft/markitdown#security-considerations)：转换器使用宿主进程权限；上传附件场景应选受限的文件流/本地转换入口，不能把用户输入直接交给可访问任意路径和远程地址的通用入口。

### 格式与处理建议（非已验证支持矩阵）

| 用户要求 | 建议路径 | 需明确的限制 |
| --- | --- | --- |
| TXT、MD、源代码 | 直接读文本，保留编码、代码结构与来源 | 不执行源码；长文件需明确分段或截断提示 |
| HTML 文件 | 提取正文与结构，作为附件资料 | 不执行脚本；不因链接或嵌入资源自动扩展访问范围 |
| DOCX | 评估 MarkItDown 转 Markdown | 嵌入图片、复杂版面及表格需要质量验证 |
| docs / 可能的旧版 DOC | 保留需求，确认实际格式后选择转换路径 | 当前未确认 MarkItDown 的旧版 DOC 支持，不静默排除该格式 |
| XLS、XLSX | 评估 MarkItDown 提取工作表与表格内容 | 不将文字提取承诺为公式重算、宏执行或完整图表理解 |
| PDF | 文字提取；扫描页按 OCR/视觉能力处理 | 空提取或部分提取必须显式显示，不能假装已读完 |
| 图片 | 视觉模型理解，可结合 OCR | 图片类型清单、识别质量及外发范围待确定；不能只提供 EXIF 就称支持 |

按已确认边界调整后的候选流程：保留原始附件与来源 → 使用 aiw file-convert 获取文本（具体契约待提供）→ 对确需视觉理解的内容另按允许能力处理 → Worker 带来源分析 → 正式目标和计划可追溯引用。不是要求 Worker 所在进程原生解析全部二进制格式，也未确定转换进程部署位置。

## 建议的产品边界（尚未确认）

- 每个草案具有独立身份、对话及当前内容；用户可切换多个草案，Worker 不应串用目标、知识范围或工作区。
- 草案内容与聊天记录有关联，但不是同一份数据；人工编辑与 AI 建议需可区分，避免后到的回复覆盖用户修改。
- Worker 可通过 Skills 辅助澄清、分析和草拟计划；具备 Skill 不等于获得创建、批准、执行或发布权限。
- 项目知识、其他知识库、工作区与工具能力显式绑定和选择；读取或分析能力不能隐含获得写代码、安装依赖、任意 shell 或外部访问权限。
- 工作区分析结果附来源和版本；无法访问或工具未安装时说明限制，不伪造分析结果。是否必须自动构建索引尚未确认。
- 转正式产出正式目标；是否同时创建计划草案由用户选择。建议展示交接快照和缺失项；不将目标转正或自动补全 Steps 视为已经批准、启动执行或完成业务计划。
- 目标草案、正式目标内容、下游计划草案建议保留来源及版本关联，并防止重复请求创建重复计划；转正后是否可继续编辑、重新转正或更新下游计划仍待确认。
- 删除草案的范围、恢复能力及运行中回复如何处理待确认，不预定硬删除或级联删除。
- UI 以现有深色控制台为基础，运用目标/任务卡片、Worker 状态和适量动效表达科幻游戏风；可读性、操作状态和键盘使用应可判断。
- 运行后端可选择 Codex 与 OpenAI 路径；默认优先采用 OpenAI 路径。“SDK / API”是否都需独立支持、如何选择默认路径待确认；失败时不建议静默切换提供方、模型或扩大工具权限。
- 本需求 Worker 的职责为目标讨论及所选分析/规划，不自动继承 ISSUE-00006 的代理审批或其他决策权限。是否共享身份认证设施可在后续设计评估。

## 目标验收例（提议，未运行）

1. 用户创建草案 A、B，各自进行多轮讨论；切换后能恢复对应上下文，A 的内容和项目资料不会误写到 B。
2. 用户编辑目标内容后，新到达的旧上下文 AI 回复不能静默覆盖编辑；界面明确展示保存、生成、失败或冲突状态。
3. 用户可查看与选择已配置的项目知识和其他知识范围；Worker 引用可追踪证据，无法获取时说明限制。
4. 用户可请求对所选工作区做允许的 research/代码分析；结果关联来源快照，未授权操作不执行。
5. 用户从含糊描述开始，Worker 通过讨论指出并澄清缺失信息；转正后得到适合 Worker 理解的目标内容，而不是创建 AIW Issue。建议保留原始表达、确认决定及来源关联。
6. 不选择附加操作时只整理正式目标；选择创建计划时，将目标带入新的计划草案。AI Steps 可用时触发分析并补全步骤；分析不可用、失败或无法补齐必要信息时，保留已有目标和可用步骤，在编辑页面显示原因及待补充内容，允许人工继续，不伪造步骤、不自动启动执行。
7. 删除行为符合确认后的保留策略，晚到的 Worker 回复不能复活已删除草案或污染其他草案。
