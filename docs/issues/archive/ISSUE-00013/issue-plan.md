## 使用者、问题与目标

用户获得与目标范围相符、包含代码版本和真实验证证据的正式交付；下游能按固定输入继续工作；平台重启或执行失联后可以恢复或明确报告阻塞，所有实际工具操作遵守本次授权。

## 范围与规则

1. 任务携带目标、输入、范围、验收条件及输出约定；下游依据正式成果，无须继承上游完整对话。优先复用 TaskInput、输出模块和 Git 提交引用。
2. 专业配置、Skills、正式报告及代码能定位版本或内容哈希；上游更新不静默改变在途依据，受影响工作通过补充或替代处理。
3. 并行代码修改使用独立工作空间及明确基线，通过集成工作汇合。Agent 可报告阻塞、澄清或建议拆分，由统一平台入口协调跨任务影响。
4. 是否独立审核由计划和策略决定，小任务不强制经历所有专业角色；不把模型自述当作已执行验证。
5. 工具需求与实际授权分开；平台决定本次操作及资源范围，在真实调用边界执行。任务或委托授权不等于全部工具许可；计划、配置及报告不得自行扩大目标、权限或预算。
6. 重启、失联及重复事件后依据持久记录恢复或等待处理，不依赖模型记忆。重复事件不能重复创建任务；外部操作结果未知时先核对，避免盲目重做。

## 已确认：循环追加授权边界（2026-10-22）

来源：用户确认默认最多 3 次业务回跳（初始另计，共最多 4 轮），到限申请授权；秘书只有获授审批权限时才能按 policy 处理。循环行为由 [ISSUE-00010](../ISSUE-00010/issue-plan.md) 拥有，申请及秘书交互由 [ISSUE-00012](../ISSUE-00012/issue-plan.md) 拥有。

- 追加必须具备与具体工作、作用范围及新增额度关联的有效决定，平台保存正式申请、决定与生效记录。授权循环追加不自动授权其他工具、资源、模型升级或预算扩张。
- 秘书代审批时，仍须核对其真实代理身份、当前有效委托、适用 policy 及事项状态；秘书不能自行创建、续期或扩大自身审批权限。policy 判断不能替代实际授权。
- 无授权、超范围、规则冲突或无法判断是否适用时，继续由用户决定；撤销或失效的委托不能支撑新的代理决定。
- 追加保留历史消耗，不能通过换 Worker、重启或换一份授权清零。同一决定不得重复增加额度或重复推进。每次新增额度与作用范围由申请及决定明确，委托有效期和 policy 由用户实际配置；后续追加仍须有效决定。
- 复用参考：[ISSUE-00006 的既有有限代理授权规则](../archive/ISSUE-00006/issue-plan.md)，包括人类优先、有效授权与累计额度约束；这里只引用约束，不修改其既有批准、FD 或交付范围，也不宣称相关运行能力已验证。

验收例：无审批委托的秘书不能使追加生效；有效委托仅能覆盖明确范围；撤权后未生效的代理决定不能继续生效；重复提交同一决定不能重复增加额度。此为后续验收目标，不是当前测试结果或真实授权。

## 已确认：业务监测、安全处置与行为审计的边界（2026-10-22）

- 业务监测与安全处置需要不同授权，通常分属两个 Worker；分别校验操作、资源、身份、任务及有效授权，分类或共用目录不能替代授权检查。
- 通常由两个 Worker 承担不构成固定实例数或常驻策略；更换执行者不能继承另一类任务权限。
- 行为审计以实际行为、授权和规则遵守证据为对象；需求本身的审议由需求评审职能承担，审计分类不产生额外审批或执行权限。
- 知识归知识管理职能，知识访问及输入继续遵守授权与版本要求；不改变用户侧私人数据边界。

验收目标：持有监测授权的执行者发起未获授权的处置被拒绝；行为审计依据真实证据，需求评审处理需求矛盾；任何分类中的执行者都不能凭职能名称发布、访问受限数据或处置。本轮只更新需求，不启用实际权限或服务。
