## 1. 使用者、问题与目标

当前使用者是本地单机系统的个人用户。用户希望与秘书 Worker 对话，让它理解并安排工作、在约定时间将工作提交执行队列、查询进展、跟踪结果并按需要反馈。等待未来任务期间，用户仍能与秘书继续讨论其他工作。

“部署 Worker”只是专业 Worker 的示例，不是本需求固定的业务种类，不要求为此必建 Jenkins、部署或生产发布能力。是否能够安排某种具体工作，取决于平台实际支持的能力、Worker 和有效授权；无法执行的事项必须说明限制。

业务目标：让用户可以把经过澄清的意图交给秘书安排，同时保留对任务内容、时间、权限和执行状态的控制。任务安排、入队、执行中、业务结果与通知送达必须能被区分，不能用聊天中的承诺代替平台事实。

### 2.3 调度与异常

| 情况 | 用户确认的规则 | 尚不能推导的内容 |
|---|---|---|
| 系统休眠或停机，错过原安排时间 | 重新确认后再执行；首期按分钟粒度处理，见下方补充 | 不默认恢复后立即补跑，不另设每个安排的延迟容忍参数 |
| 指定 15:00 | 以分钟为单位安排到期入队，不要求秒级准点 | 不保证实际开始时间或完成时间；Worker 和资源不足时仍可能等待 |
| 安排后内容发生变化 | 需要确认是否执行最新内容 | 不自动采用最新内容，也不假定可以继续执行旧内容；需展示变化及确认对象 |
| 用户取消 | 区分尚未触发、已排队、执行中及已经产生外部副作用 | 取消不自动代表停止成功或已回滚 |
| 外部请求已经发出但结果不确定 | 先核实结果或转人工 | 不盲目重试可能产生重复副作用的动作 |

2026-10-20 用户补充：先不要复杂化，参考 crontab 的做法，调度精确到一分钟，允许由这一粒度带来的少量延迟。撤回整理者此前提出的“每个安排配置可接受入队延迟”的建议，首期不新增该配置。

整理理解用于验收：15:00 表示在 15:00 这一分钟内触发入队，不把正常的秒级偏差当成需要再次确认的错过。系统停机等原因真正错过目标分钟时，仍沿用重新确认的已确认原则。这个口径是本产品的分钟粒度安排语义，不是对所有 crontab 实现延迟行为的保证，也不表示已经选定调用操作系统 crontab。

原始草稿提出的一次性、重复、延迟和条件后续安排仍是候选能力范围；本次回答并未批准它们全部进入首期，也没有取消这些候选目标。

## 3. 当前 Plan 模块的静态评估

结论：现有 Plan 可复用为工作执行与跟踪的基础，但不能直接、不加区分地承接全部秘书工作安排。以下均为源码静态观察，未证明运行时通过。

| 证据 | 当前事实 | 对秘书安排工作的影响 |
|---|---|---|
| `workflow/domain/WorkflowPlanSpec.java` | 目标、来源、1–32 步；每步含能力、skillRef、指令、依赖、工作区及模型偏好；无 executeAt、时区或错过触发策略字段 | 可以表达有限步骤的委派输入；不能把当前 Plan 当成已实现的持久时间安排 |
| `workflow/domain/WorkflowPlan.java` | 状态为 DRAFT、CONFIRMED、WITHDRAWN、STOPPED；保存版本与创建/更新者字符串 | 可以复用版本和审计线索；不能从操作者字符串推导稳定所有权、访问权或 Worker 雇佣关系 |
| `WorkflowPlanService.draft/confirm` | 草稿不产生业务任务；确认通过状态/版本检查后立即创建首步执行任务 | 直接提前 confirm 不能表达“等到约定时间才入队”；需要在执行入口之前明确持久安排及授权条件 |
| `WorkflowEditorService.ROLES/validateSpec` | 接受 requirement-analysis、solution-architecture、implementation-planning、coding、integration、repair 对应角色与 skillRef | 任意通用 Worker 或部署角色不能靠填一个 capability 就自动成为受支持的 Plan 步骤；需评估受控扩展 |
| `WorkflowStepCompletedHandler`、`WorkflowPlanService.createReview` | 步骤执行完成后生成独立 workflow-review；按步骤顺序推进；REPAIR_REQUIRED 在自动额度内生成下一轮执行 | 现有逻辑面向开发流程。不能默认普通提醒、查询、外部操作都需要相同评审与再次执行策略，尤其不能让返工隐含重复外部副作用 |
| `WorkflowPlanController` | 管理动作使用会话操作者、角色及版本检查；提供确认、取消、停止、跳转等入口 | 秘书或定时任务不能通过伪造 actor 字符串冒充人类确认；新增调用路径需要真实身份与有效授权 |
| 当前 Plan 文档 | 现有产品以 Flexible Plan 为主；固定自主 Run 入口已退出当前产品 | 沿用当前 Plan/WorkTask 权威，不按旧 Handoff 新建一套 Run/Task 生命周期 |

这里的 `workflow/...` 路径均位于 `src/main/java/me/asu/aidev/` 下。现有 Plan 取消/停止机制可作为复用基础，但不证明它能撤销任意外部系统已产生的副作用。

## 4. 工程建议与取舍（不是用户已批准的实现方案）

1. **通用 Chat 能力与业务 Worker 职责分开。** 评估复用会话、消息、附件、上下文版本和工具调用能力；需求分析 Worker 与秘书保持不同业务规则、授权和上下文范围。不能借复用 Chat 静默扩大 ISSUE-00007 的范围。
2. **复用 Plan/WorkTask，不复制执行权威。** 多步骤、需阶段验收的工作优先评估映射到 Plan；纯状态查询不必为了复用 Plan 而生成执行计划。普通工作按类型确定完成与核验条件的原则已确认，具体契约待设计；开发 Plan 保留独立评审。
3. **安排与执行分开。** 安排记录表达约定时间、绑定的工作内容和确认依据；到期后经当前授权及内容检查，再进入现有队列。单机模式也应持久保存安排，不能只靠秘书对话或进程内计时器。
4. **先记录归属与代表关系。** 单机可以映射一个默认本地用户；业务上保留资源归属、实际操作者、所代表的授权人和 Worker 身份。具体字段、关联和旧数据迁移留给 FD；不能把 createdBy 等审计字段自动当成完整访问控制。
5. **为未来的共享和雇佣保留边界。** Worker 所有者、任务委托者与资源访问权不是同一概念；未来允许使用某个 Worker，不自动意味着该 Worker 可以看到双方全部对话、知识或凭证。当前只要求不把这些关系写死成全局同一身份，不实现交易或租户平台。
6. **通讯按场景选择。** 可优先评估复用现有 HTTP 受理命令与查询、持久事件传递异步结果、MCP 作为 AI Runtime 的适配入口。是否需要独立 eventbus 服务及最终通讯组合待现状核验；任何入口使用相同业务权限校验。
7. **单机模块化部署优先。** 保留现有数据库和 Worker Pull；资料归属上下文也应作用于后台任务、检索、文件、凭证、通知与审计。未来多用户发布前仍需完整认证、隔离与迁移验证，不承诺仅新增账号表就完成升级。

### 4.1 新增候选：独立 Plan 协调 Worker（尚未确认）

用户提出：当前由平台处理 Plan 任务推进，是否应由独立 AI Worker 处理，平台提供流程说明书和基础工具。本段记录架构探索，不视为用户已经决定迁移现有 Plan 或授权实施。

这里需要区分三项职责：约定时间到期触发、任务的 Worker Pull/资源准入、Plan 的步骤推进与异常协调。独立协调 Worker 主要讨论第三项；不因为把协调外置，就让 LLM 接管可靠时钟、租约归属或并发额度。

| 候选 | 收益 | 主要代价与边界 |
|---|---|---|
| 继续由平台按已定义规则推进 | 固定开发流程路径明确，减少外部调用与恢复状态 | 目前角色及推进策略写在 Java 中，扩展业务流程需要改代码 |
| AI Worker 读取自然语言说明后决定所有推进 | 能解释开放问题、提出新步骤及协调异常 | 每次固定推进也依赖模型，增加等待、费用与结果不确定性；说明书中的约束不等于可强制执行规则 |
| 可独立部署的协调 Worker 解释版本化流程，必要时调用 AI | 流程扩展与平台执行基础分开，保留动态决策能力；固定路径可直接按规则推进 | 需持久保存协调进度、事件恢复、重复处理及并发控制；平台仍强制校验合法动作与权限 |

整理者当前建议第三种作为评估方向，而不是立即整体重写：平台提供版本化流程定义、事实记录与受控的原子业务命令；协调 Worker 读取当前状态和证据，决定并请求下一步。明确规则如“独立评审 PASS 后进入已声明的下一步”不必调用模型；开放问题、复杂证据判断、异常处置或计划调整才需要 AI。

流程定义应表达可校验的前置条件、允许转换及完成条件，自然语言说明用于解释业务意图。平台不能仅提供任意 CRUD 或 shell 工具，把所有约束交给提示词；它仍校验当前版本、动作是否合法、真实身份、资源范围、授权、额度、评审独立性，并持久提交结果。协调 Worker 离线不能丢失 Plan，重复或并发请求不能产生重复有效委派；若未来迁移，原平台推进和 Worker 推进不得同时成为同一计划的独立执行者。

秘书负责用户交互和工作安排，协调 Worker 负责一个 Plan 的过程管理，专业 Worker 负责具体工作。协调者执行 ISSUE-00006 所涉批准或其他代理动作时仍需对应授权及独立性，不因协调角色自动拥有批准权，也不默认可以自行增删步骤或绕过评审。独立角色不要求单机首期启动额外的常驻 LLM 会话或独立服务。

这一候选还需要明确“流程可配置”的需求和“允许运行时改变计划”的需求是否都成立；用户当前只提出可能性。固定流程与动态 Agent 的取舍参考 [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，它区分预定义工作流与由模型动态决定路径的 Agent；此资料不证明本项目任一改造方案已通过验证。
