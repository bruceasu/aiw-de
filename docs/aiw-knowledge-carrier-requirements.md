## 1. 已明确的方向、假设与证据

**用户已明确：**

- AIW 需要知识库载体，承载工作所需的知识与参考资料。
- Agent Factory 教材及其配套仓库作为参考资料。
- `D:/03_projects/AI-tools/knowledge-base` 是候选载体，也是新项目，可以根据实际需要调整。
- 当前先记录需求，后续再决定如何改造。

**工作假设：**

- 首期围绕软件工程 Worker：需求分析、架构、实施规划、实现、Review 和 Verification。
- 资料需要同时服务人类查阅和 Worker 检索；Worker 可能运行在不同进程、机器和运行时。
- 初期可以从少量精选资料开始，不要求一次导入整本教材或所有历史记录。

跨机器范围、用户数量、权限模型、资料规模和可接受成本尚待确认。

**已有静态证据：**

knowledge-base 的 README、用户文档和局部代码显示，已有文档导入、SQLite 权威状态、Lucene BM25 projection、来源与内容 hash、Canonical/Derived 知识模型、带证据的上下文构建，以及六个本地 stdio MCP 工具。当前单进程独占一个 workspace；HTTP 无内建认证/TLS，MCP 无网络 listener。

本次依据之前的静态阅读记录，不代表完整代码审计或运行通过。详细来源见[参考价值研究](agent-factory-reference-assessment.md)，以及 knowledge-base 的 [README](../../knowledge-base/README.md)、[用户手册](../../knowledge-base/docs/user-guide.zh.md)、[领域模型](../../knowledge-base/CONTEXT.md)。

## 2. 目标与职责

目标：Worker 在执行具体任务时，能够找到适用知识、定位原文、获得有预算限制且可追溯的上下文，并明确知道哪里存在过期、冲突或缺失证据。

| 责任 | 所属系统 |
|---|---|
| 任务状态、租约、调度、执行记录、工程门禁、人类审批 | AIW Control Plane |
| 原始资料、知识版本、来源、检索、关系证据、上下文组装 | knowledge-base |
| 工具使用、代码修改、提交知识改进候选 | Worker |
| 正式知识发布、权威级别、适用范围及争议处理 | 指定的人类维护者／审批者 |

知识库中的“建议发布”“审批通过”等文本不构成 AIW 的执行授权。需要实时状态时，应访问拥有该状态的系统；知识库可以保存历史证据和链接，但必须标明观察时间。

## 3. 需要承载的知识

以下是建议需求，需在后续设计阶段确定首期范围。

| 类别 | 内容示例 | 使用约束 |
|---|---|---|
| 外部参考 | Agent Factory 教材、官方文档、论文 | 保留原出处，默认不作为项目强制规范 |
| 内部通用规范 | 工程原则、开发流程、通用安全规则 | 维护者批准后发布，明确适用范围 |
| 项目知识 | 架构、ADR、接口约定、仓库规则 | 按项目与版本限定，避免跨项目误用 |
| Worker 角色知识 | 职责、Skill、输入输出、异常升级 | 版本化，关联评估与授权边界 |
| 任务依据 | 已确认需求、验收条件、设计、代码基线 | 绑定任务及 revision，区分草案和已确认内容 |
| 经验与评估资料 | 失败案例、修复经验、人工判定、rubric | 脱敏、审核；候选与已发布资料分开 |

导入内容可能包含 MDX/JSX、代码块和教学命令。正文提取必须保持可读性与来源位置；这些内容不应在导入或检索时被执行。教学提示或外部指令也不能改变当前 Worker 的系统规则和权限。

## 4. 核心能力需求

### K-01：资料导入与同步

- 支持选定目录、文件及 Git 版本资料；首期重点是 Markdown，明确 MDX 的处理策略。
- 支持允许目录／排除目录、重复内容识别和增量更新；历史归档默认不混入当前知识。
- 保留更新、删除和导入失败的状态；同步方式必须明确，不能默认存在后台监听。
- 记录导入批次、来源、内容 hash、导入时间和错误；为教材更新保留版本差异。
- 复制或镜像外部目录时保留原始路径映射，避免知识库内路径被误认为源路径。

### K-02：来源、版本和适用性

- 每个知识对象有稳定身份；具体版本可独立引用，内容变化不静默改写历史引用。
- 记录原始 URI／仓库、文件、章节／范围、Git revision 或来源版本、内容 hash。
- 区分原文、摘录、摘要和生成内容；生成内容记录生成者／版本及消费的源版本。
- 记录项目、角色、主题、资料类型、生命周期、维护者、批准状态及适用时间等必要 metadata。
- 区分“源文档原文”与“本组织认可的正式规范”。Canonical 身份不自动表示法规或项目权威。

### K-03：检索与原文读取

- 支持关键词检索、项目／角色／资料类别／版本过滤、稳定对象与版本的直接读取。
- 结果返回引用、来源位置、适用范围、新鲜度及排序理由；限制结果数量和正文长度。
- 排序考虑适用性、权威级别和新鲜度；相似度不能决定哪份规范有效。
- 明确无结果、资料不存在、版本不可用、索引落后和源服务失败的区别。
- 保留中文和英文资料检索能力。BM25 可作为首期基础；是否增加向量／混合检索，由代表性查询的评估结果决定。

### K-04：任务上下文包

- 请求包含项目、任务／attempt、角色、意图、代码基线、必要知识版本和 token／响应预算。
- 输出包括任务依据、适用规范、参考资料、稳定引用、来源版本和新鲜度。
- 显式列出冲突、遗漏、过期材料、缺失证据，以及结果是否完整；不把不足证据包装成完整答案。
- 保留来源元数据，摘要压缩不丢失版本和适用性。
- 允许保存上下文清单或快照标识，使后续可以解释某次 attempt 当时使用的资料。
- 运行中的资料更新有明确策略：优先绑定既定版本；关键资料撤销／安全更新时如何刷新或停止，需要另行决定。
- token 数可能是估算，返回估算方法／版本，不能宣称所有模型 tokenizer 都精确一致。

### K-05：多 Worker 读取和接口契约

- 多 Worker 可以读取同一个已发布知识集合，复用语言无关的结构化契约。
- 对搜索、读取、trace 和上下文建立统一的 schema version、状态、诊断和预算表达。
- 把知识读取与维护写入分开；Worker 默认只读，写入经验需经过候选提交和审核。
- 远程 MCP、HTTP 或本地代理是候选接入方式，后续选择；不预设必须新增一种 transport。
- 同一 workspace 的存储应有一个明确服务 owner；不能让每个 Worker 各启动一个进程同时打开它。
- 定义调用取消、超时、并发上限和响应限制；重试策略待实际调用模型明确后设计。

### K-06：权限与资料治理

- 单用户本地场景与跨机器共享场景分别明确身份和信任边界。
- 共享时支持按用户／Worker／项目限制资料；在检索、原文读取、trace、上下文和缓存中一致执行。
- 项目过滤不等于权限控制；调用者不能通过修改 projectId 获得其他项目资料。
- 对敏感信息、凭据和生产轨迹明确导入、保留、脱敏及删除政策。
- 发布记录维护者、审批者、原因和版本；Worker 不能自行提升资料权威、降低评估条件或扩大权限。
- 撤销资料后明确旧引用的显示、历史留存和继续使用策略。

### K-07：经验与评估闭环

- 失败 attempt 可产生待审阅经验条目，关联任务、代码／知识／Skill 版本和原始证据。
- 审核后可晋升为正式经验、评估案例或 Skill 改进提案，保留晋升记录。
- 评估集、rubric 和人工标注独立版本化，覆盖正常、失败、冲突、过期和权限边界。
- 知识库保存评估资产和结果依据；模型调用与评估执行由哪个系统负责，另行确定。

### K-08：可运维与可解释

- 观察导入状态、业务／索引 checkpoint、freshness、检索延迟、上下文大小和诊断。
- 记录必要的查询／上下文使用审计，并限制敏感正文进入日志。
- 索引可从权威记录重建；备份恢复包含资料、版本、metadata 和证据。
- 服务不可用时，必要规范缺失应明确中止或升级；可选参考资料缺失可以降级并报告。每类任务的策略由 AIW 定义。

## 5. knowledge-base 已有基础与候选改造

| 需求方向 | 已观察到的基础 | 后续需要确认／改造 |
|---|---|---|
| 导入同步 | 显式 ingest/sync、hash 与 projection 恢复 | 教材范围选择、MDX、原路径与 Git revision 映射 |
| 版本来源 | SourceRef、Canonical/Derived、文档 revision | 不可变引用、发布状态、适用时间及权威规则 |
| 检索 | Lucene BM25、结构来源、虚拟项目范围 | 中英文资料效果、过滤和排序策略；向量检索按需 |
| 上下文 | intent、token budget、provenance、diagnostics、omissions | AIW task/attempt 关联、版本固定、上下文清单 |
| 接入 | 六个只读 stdio MCP 工具、HTTP API | 集中读取模型、跨进程／跨机器 transport 与身份 |
| 权限 | 本地路径边界 | 共享资料授权、维护与发布权限、敏感数据治理 |
| 评估改进 | 可承载文档与证据 | 案例／rubric 版本、候选晋升、AIW 证据关联 |

用户允许按需调整新项目，后续可以重新审视接口、部署和领域模型，不必拘泥于现状。但具体 schema、兼容性、迁移和数据保留仍应在设计中明确，不能把“新项目”视为所有现有数据都可丢弃。

## 6. 建议的最小切入范围

先围绕 Code Review Worker 做一个知识使用样板：

1. 精选 Agent Factory 的规格、上下文和评估材料，以及 AIW 架构、规范和角色说明。
2. 为每份资料标明外部参考／内部规范、项目范围、来源和版本。
3. 定义一次 review 任务怎样请求知识，以及怎样返回引用、缺失和上下文清单。
4. 在现有集中 HTTP 与本地 MCP 之间明确首期进程模型；如需远程 MCP，再设计 transport 和授权。
5. 准备人工标注的代表性查询，判断检索与上下文是否足以帮助 Worker。

此顺序是讨论建议，不是当前执行授权。首期暂不要求自动抓取全网、多租户集群、自动知识发布或自修改 Worker。

## 7. 后续设计应回答的问题

- 首期是同机使用，还是多机器 Worker 共用？预期并发、资料量及维护者人数是多少？
- 哪些资料必须被视为正式规则？谁能发布、撤销、解决冲突？
- 外部资料使用本地镜像、定期同步还是在线检索？如何处理许可、更新和源服务失败？
- 任务固定知识版本到何种粒度？任务进行中规范撤销如何处理？
- 一个共享 workspace 是否足够？项目分区与真正的访问权限怎样对应？
- Knowledge API/MCP 的已有契约是否保留？如果调整，怎样迁移客户端与已有数据？
- 哪些审计和上下文需长期保留？敏感资料如何删除，历史引用如何呈现？
- 哪个系统执行知识／Worker 评估，谁维护案例，什么条件可以发布改进？
