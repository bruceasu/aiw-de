# 目标讨论工作台

从 Web Console 的 Goals 进入。先保存目标正文、缺失信息和选择的项目知识，再发送消息；Worker 建议只进入聊天记录，由用户显式更新正文。切换目标或离开页面后，已保存的目标、聊天、附件、正式版本和计划编辑内容仍保留。尚未保存的浏览器编辑需先保存或明确放弃。

工作台使用现有控制台账号的 actor 隔离。认证关闭时全部浏览器属于 `local-console`；这不是匿名浏览器隔离或新增多租户认证。讨论任务及其输入进入现有运维可见面。点击“准备执行计划”时明确确认交接到既有操作员可见的 Plans；数据库管理员和原管理 API 不受工作台的界面隔离承诺约束。

## 删除与恢复目标

左侧默认显示“当前目标”，每个目标旁可直接点击“删除”，无需先打开详情。确认框会显示目标名称；取消不会提交。删除当前目标后详情关闭，删除其它目标保留原选择。未保存的目标或计划编辑需先保存，或用原有重新加载入口明确放弃。

删除、切换列表丢弃消息、放弃编辑重新加载及准备执行计划均使用控制台统一弹窗。删除为危险操作样式，取消保留原内容。确认删除后请求显式发送 revision 和 confirmed，恢复、步骤分析及应用同样提供完整请求字段，避免严格 JSON 解析因缺失布尔字段而拒绝请求。

删除是可恢复操作：在“已删除”中点击“恢复”，再到“当前目标”打开。原目标内容与正式版本保留，旧待处理讨论回复不再写回；已创建的执行计划和工作区不会连带删除。列表数量只统计接口返回的最近 100 个目标，不代表全部历史。可用“刷新”核对当前状态；请求结果未确认时不会自动重复删除或恢复，明确成功后刷新失败会单独提示。

删除只有提交前的确认弹窗，没有提交后的审批或第二次确认。服务器拒绝时显示错误原因；连接中断、服务器异常或返回内容无法读取时，页面显示“结果暂时未知”及“核对操作结果”按钮。该按钮按原目标读取当前状态，不会再次删除或恢复，也不依赖最近 100 条列表。读取失败可再次核对；核对成功显示当前已删除/未删除状态，并保留详情中的本地编辑。若详情仍打开，请先复制未保存文本，再重新加载已保存版本。读到的状态只代表读取时的结果，无法证明具体是哪一次请求造成。

## Worker 与后端

工厂 Worker 按角色、仓库、运行时、模型、推理强度和启动路径等实际兼容配置标识；重复保存同一设置不会产生新 Worker ID。兼容的在线 Worker 会继续接收任务；进程退出且没有未恢复租约时，下次需要它会使用同一 ID 重新启动并注册。

工厂创建且已离线或心跳过期的 Worker，在没有活动租约、运行中任务或尝试后，会自动退出注册列表及相关选择项；任务和审计历史保留。重新注册后会恢复显示。只凭 `factory-` 名称前缀不会移除外部 Worker；旧工厂记录需有本机工厂状态回执证明来源。在线空闲 Worker 保留供复用，不按每次任务完成就退出。

管理员可通过 `POST /api/r1/worker-registrations/{id}/unregister` 注销已经离线或心跳过期且没有未完成执行的普通 Worker，提交心跳快照 `expectedHeartbeatMs` 和原因 `reason`；使用控制台会话及 CSRF。人工注销单独记录，不赋予工厂归属。注销后不再出现在注册列表和相关选项中，任务历史保留；重新注册可恢复显示，普通心跳不会取消人工注销。

正式目标版本、执行草案和已确认执行计划是不同状态。确认执行通过原计划 confirm API；只有 CONFIRMED 原生计划的 READY 工作会触发工厂按需启动对应角色，已有兼容在线角色（即使忙碌）优先复用。尚未开始的原生执行草案可由原人类所有者通过 `/api/r1/plan-editor/plans/{id}/execution-target` 明确修改已登记的仓库和 Git 基线；保留原计划 ID 和正文，托管计划继续使用原范围管理。不会自动批准历史草案。

工厂已配置模型且启用“自动启动 Worker”时，目标讨论会在没有匹配在线 Worker 时请求启动内置 `goal-discussion` 角色，沿用选择的后端和工厂默认模型。它只生成文字，不绑定项目仓库、不启用动态执行配置和文件工具；外部讨论 Worker 仍可自行接入。启动失败、工厂未启用或所选后端不匹配时，在讨论按钮旁显示具体原因。

发送成功后显示排队状态，仅在当前目标存在待处理讨论且没有未保存编辑时，每 3 秒检查回复，最多 40 次；随后可手动“检查回复”。自动更新保留未发送消息，不覆盖目标正文或未保存编辑。正式版本保存结果在按钮旁显示，并定位到保存的版本；有缺失信息但未勾选接受时，使用统一确认框明确询问，不会默默取消或直接批准执行计划。

独立角色 `goal-discussion` 已在 TypeScript、Python、Go 三包实现，共享角色与 Skill 契约。TS/Python 用 `AIW_PROCESS_ROLE=goal-discussion`（TS 的 start:all/管理器 all 也包含它），Go 用 `profiles/goal-discussion.toml` 启动。默认 OpenAI backend 接受 TS/Python 的 `openai-agents` 和 Go 的 `openai-api`；显式 Codex backend 接受 TS/Go 的 `codex-cli`/`codex-app-server` 及 Python 的 `codex-app-server`。Python 已删除 `codex-sdk`，需显式迁移旧配置。Python App Server 已支持原生 Windows，沿用本机 CLI 登录；讨论请求使用共享的纯文字模型模式，关闭原生工具。完整 [角色/语言/后端矩阵](../../workers/README.md) 记录其他运行时的支持边界。没有在线匹配 Worker 时显示原因，人工编辑仍可用。

未启用工厂自动启动时，选择 Codex 仍需已有的外部讨论 Worker。在已有平台地址和 Worker 凭证的环境中，可用 PowerShell 手动启动：

```powershell
$env:AIW_AGENT_RUNTIME = 'codex-app-server'
./workers/process-python/scripts/run-role.ps1 goal-discussion
```

步骤分析使用独立的 `planner` 角色。工厂已启用自动启动且模型匹配时，提交分析会自动启动该角色；查询可用性不会启动进程。未启用工厂时仍可连接外部 planner。分析只根据正式目标生成步骤建议，使用独立临时目录及纯文字模型模式，不获得文件或执行计划的权限。讨论 Worker 同样不会自动获得实现或执行计划的权限。

每次发送冻结完整已保存对话、当前正文、缺失清单、选择的项目知识和本次明确同意外发的附件文本。配置 AI Profile 时只允许对应后端的已批准配置；缺少匹配配置不回退到其他后端。三语言的 OpenAI 讨论角色均不提供文件、shell 或 AIW 工具。讨论使用独立空临时目录并拒绝意外工作区 assignment，避免读取运营者的默认源码目录；Codex 仍依赖宿主沙箱边界，空目录不等于操作系统访问隔离。此版本不自动执行工作区 research；可显式选择既有项目知识或上传分析资料。其他知识库和新索引平台不属于首版。

每目标上限 100 条已有消息；模型输入上限 60000 字符，超限明确拒绝，不静默截断。Worker 报告为 1–16000 字符的建议文本；失败、无效报告和旧输入有明确状态。人工编辑不被晚到建议覆盖；删除/恢复后的旧请求不能写回。点击“检查回复”获取结果；重进工作台仍能查询未完成请求。

## 附件

每目标最多 20 个附件，每个 1 字节至 10 MiB。原始字节保存在数据库中（base64），下载按目标归属检查。没有文件自动执行或远程 URL 抓取。

点击本地转换时通过固定参数调用 `aiw file-convert -i <随机本地文件> -o - --format md`，最长 30 秒、文本输出最多 256 KiB，不使用 shell，不安装依赖。需由运营者预先配置 AIW 命令及对应格式的离线后端。用户提供的命令 help 是本次接入依据；未假定或解析未知 JSON 响应。

转换失败、空提取或后端缺失保留原件并显示状态。图片的文本转换不代表视觉理解，显示需要视觉复核，不能作为已理解文本发送；扫描 PDF 可能需要 OCR/用户补充可读文本。非空 PDF 输出也可能遗漏图片或扫描页，发送前需查看提取结果。本功能没有自动启用视觉服务。源代码、HTML、Office 文件和转换文本均视为数据，不执行其指令、脚本或宏。

附件默认不进入模型输入。每次消息需勾选明确的外发选项，只有 `TEXT_EXTRACTED` 状态可发送。选择的项目知识随保存选择进入下一次讨论，始终附来源 ID 与哈希。

## 正式目标与计划

缺失清单非空时，必须勾选接受缺失才能创建正式版本；该版本仍显示未就绪，缺失清单进入后续计划目标。再次修改目标产生新版本，既有正式版本及计划输入不变。重复正式化同一草案 revision 返回同一版本。

正式版本自带可持久保存的计划编辑快照，允许零步骤或不完整步骤；它不同于校验通过的 `WorkflowPlan`。可选同时请求 AI Steps；推荐不可用时保留人工编辑路径。点击检查/应用后，仅当编辑 revision 仍匹配才填入建议步骤。保存新编辑后可重新请求分析。计划编辑快照最多 32 步、128000 字符，不会放宽既有实际计划保存校验。

HTTP 接口将正式版本的 `snapshot` 和 `editor` 转换为普通 JSON 对象，再交给 Spring MVC 输出；提交编辑也先接收普通对象，再转换到内部树模型。这样避免 Spring Boot 4 的 Jackson 3 将内部 Jackson 2 节点当作 Java Bean，导致页面只收到 `nodeType` 等类型属性而丢失目标与步骤。

AI Steps 提示包含完整步骤字段、key 格式和依赖规则。具体代码需求的建议应包含编码步骤，不能只生成“继续制定实现计划”的循环；结果仍按现有模型严格校验，无效建议不会自动应用。

用户明确点击准备执行后，才为缺少工作区的编码步骤创建受管临时目录，根目录由 `aidev.goals.workspace-root` 配置，默认 `data/goal-workspaces`。Git 可用时初始化；没有 Git 时使用现有 DIRECT 模式。异常中留下的目录保留供恢复；重试使用确定的版本目录与注册 ID。默认不随目标或计划删除目录，也不自动清理。用户仍需到 Plans 页面独立确认执行，本功能不会自动 confirm/start。

## Windows 命令目录的只读对比诊断

后续授权的本机诊断没有调用模型，而是使用已安装 Codex 导出的协议，通过 `command/exec` 直接提交固定 argv 和真实存在的受管 worktree `cwd`，策略为 `readOnly`、禁止网络。结果如下：

| 固定命令 | 宿主直接执行 | Codex App Server 受限执行 |
| --- | --- | --- |
| `cmd.exe /d /c cd` | 返回所指定的 worktree，退出码 0 | 同样返回所指定的 worktree，退出码 0 |
| `cmd.exe /d /c dir /b sudoku2.htm` | 返回 `sudoku2.htm`，退出码 0 | 返回“找不到文件”，退出码 1 |

因此能确认此对比中的 cwd 已传到命令进程，差异出现在受限环境的目录内容访问，不能再只凭模型报告的 System32 断言平台丢失 cwd。文件检查失败后停止该路径，未继续尝试另一个 shell。具体沙箱/ACL 原因、原生模型工具为何报告 System32、以及 PowerShell 的实际位置仍未确定。本机配置的默认 `sandbox_mode` 为 `danger-full-access`，`windows.sandbox` 为 `unelevated`；Worker 显式请求受限策略，所以命令行可运行不等于 Worker 的执行条件相同。未修改这些配置、项目文件或权限，未重跑业务任务。

本机 Windows `command/exec` 明确拒绝自定义 `outputBytesCap`（RPC -32600）；诊断移除此可选参数后才得到上述命令回执。诊断结果仅保存命令、目录、退出码及短输出，未保存凭证或聊天内容。


### Windows 工作目录 ACL 的后续证据
