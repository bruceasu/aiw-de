# 组合角色：共用技能与角色内流程

角色由职责目标、技能组合、工作流程和整体交付要求构成。默认角色是可复制的模板；新业务角色不需要增加角色枚举、启动 Profile 或 Worker 进程。共享能力引用同一技能版本，不为每个角色复制正文。

## 使用方式

1. 打开 `/ui/configurations`，在“自定义工作方法”中点击“组合新的角色”，进入 `/ui/configurations?view=roles`。
2. 从空白开始，或导入默认模板。填写人类可读的角色名称、使用仓库、工作分类、职责和最终产出，再填写独立的整体交付要求。系统维护内部标识和版本。
3. 按顺序添加技能步骤。每步选择技能，写清做什么、何时执行和怎样算完成；条件留空表示始终执行。用上移、下移调整顺序。最多八步、六种技能和八份知识；同一技能可在多步复用，版本必须一致。
4. 预览角色，核对目标、资料、工具需求、步骤和整体交付，再明确保存。保存不会调用模型、运行命令或创建任务。
5. 点击“用于准备任务”，在原任务页面核对匹配的计划、仓库、具体任务、起始代码和已批准模型，再准备。页面选用服务器返回的精确保存引用，不从链接接受角色正文或自动执行任务。

例如，“方案研究与说明”可以先用 `research` 收集许可资料，再用 `domain-modeling` 澄清概念、用 `codebase-design` 比较接口，最后用 `teach` 或 `handoff` 形成讲解与交接。“文档修订”也可以引用同一 `research` 和 `handoff`，中间使用 `edit-article`。角色的顺序、条件和交付不同，共享方法和版本可以相同。

默认专业模板会导入原专业 Skill 和工作说明。它们保留任务、输入、来源和产出限制；例如要求 WORKSPACE 的编码技能不能直接组合成只读 REPORT。明确的产出冲突在预览/保存时拒绝。自然语言职责或材料冲突无法完全自动检测，Worker 必须报告缺口并停止依赖工作。空白角色可只选共享技能，不继承某个默认业务角色。

## 已保存角色与异常处理

列表显示角色名称、仓库、产出和版本。可直接选用原固定版本，或“复制并编辑”为一个新角色草稿；原角色和已有任务不被覆盖。复制是用户明确动作，普通刷新不会换标识或清空草稿。

保存响应未知时，页面保留原定义并锁定编辑。先“刷新并核对记录”：若相同原版本已经保存且定义一致，恢复实际保存结果；尚未发现时，允许明确重试同一原定义；内容不一致时停止覆盖。不会因连接失败自动创建另一个角色。新引用保存成功后，即使列表刷新失败也保留成功结果和精确引用。

角色更新、模板和技能更新不会追写已有任务。已准备任务、同任务重试和正式续行继续使用原配置及完整 Skill 文件字节。更换角色需按现有正式流程另行准备，不在执行中切换。

## 单 Worker 流程的含义

角色内步骤由同一个 Worker 在同一正式 Task/Attempt 中按方法遵循。顺序、条件和每步完成要求写进固定角色入口；条件是自然语言说明，不是脚本。Worker 在原结果描述字段记录已完成、不适用或阻塞，以及真实产物和检查。

这些描述不是平台逐步骤状态、强制技能调用、独立恢复或独立审阅证据。跨 Worker 的任务依赖、分支、问题和恢复仍由现有平台图编排处理。角色和 Skill 不创建任务、不接管平台状态；自己产出的结果不能因此被宣称为独立审阅通过。

模型、工具需求与执行授权分别管理。选择技能不会获得网络、命令、写入或 Git 权限。当前仅支持原有 Python 动态配置后端；没有增加 Go/TypeScript 动态配置能力。

需要判断工作是否适合隔离或并行时，可把 `delegation-planning`（委派判断）放入角色步骤；它输出有依据的建议，跨 Worker 的真实派发仍属于平台。在组合角色页点击“查看执行记录”进入 `/ui/configurations?view=observations`，按已有账本关联方法、模型、实际消耗与交付引用。上报结论不是独立验收，未采集数据不填零，记录也不增加预算限制。详见[委派方法与记录](WORKER-DELEGATION-METHODS.md)。

## 实现与兼容

`ComposedRoles.Definition` 使用 `aiw.role.composition.v1`，包含自动生成的 id/revision、自动带入的固定工程协议引用、仓库/分类、name、goal、delivery、resultKind、steps、knowledge 和 toolRequirements。每步有固定 Skill 引用及工作/条件/完成说明。

编译器生成 Owner/仓库范围的私有 Skill 资产：标准 `aiw.skill.files.v1` 包中含 `SKILL.md` 和 `role.json`。现有 Candidate 的 primarySkill 指向角色包，protocolSkills 包含工程协议及去重的步骤技能，业务名称留在 role.json。Method.name 仍为机器标识；`state.roles` 只为当前 Owner 返回友好名称、机器方法名、仓库和固定配置引用。机器标记 `composed-role-v1` 是通用执行合同，不是业务角色白名单。

新接口沿用原授权/CSRF和32KiB请求边界：

| 操作 | 输入与结果 |
| --- | --- |
| `POST .../execution-configurations/propose?kind=role` | 闭合角色定义；纯预览，返回定义摘要、候选或精确复用引用，不登记资产 |
| `POST .../execution-configurations/candidates?kind=role` | 相同角色定义；原锁和事务内登记私有文件包及不可变配置，返回 PreparedConfigRef |
| `POST .../execution-configurations/state?kind=role` | 当前 Owner 的完整 PreparedConfigRef；核对配置和角色包后返回原角色定义供复制 |
| 原 `state` | 保留既有返回键，追加 `roles` 名称/引用摘要；不返回角色私有正文 |

缺省 `kind=method` 保留原闭合 DTO 和行为。角色技术标记只能用于与 role.json 和私有资产再编译完全匹配的候选；实际引用、版本/摘要、Owner/仓库、结果和工具校验全部保留。不嵌套已生成的组合角色包。

没有新增数据库表、迁移或 Worker 传输字段，原十一份默认方法和十九个公共技能资产保持。工厂、SkillFiles 及已有 Python config-v1 消费继续固定同形 v1 配置。Control Plane 回退不再提供组合角色的创建/编辑入口；机器字段保持可解码，原冻结内容仍是唯一依据，但实际回退和运行需部署证据，不自动重建、换默认角色或删除任务。

静态检查和离线编译只支持结构及编译结论；真实浏览器、模型、Worker、逐步遵循、问答续行、数据库事务和回退效果未运行验证。本次不部署、重启、联网或执行真实任务。
