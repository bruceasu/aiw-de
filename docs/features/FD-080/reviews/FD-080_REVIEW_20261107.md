## 发现与修复复查

### R1 — P2：原生问答 successor 未由真实仓储解析（已静态修复）

初始 `effectiveExecutionId` 假设 `findCompletedInput(original)` 能解析 native formal-question slot。但实际 JdbcExecutionAttemptRepository 只通过 TaskLineage 的 execution_context 链解析，原生问答只写 formal_question_slot 并将旧任务置 CONTINUED。SELF successor 完成后，最终槽匹配不到实际成果，非最终槽也无法取得已接纳输入；纠错依赖若继续引用旧 ID，还会永久阻塞。原 mock 用例直接返回 successor，不能证明真实链路。

修复在 [NativeQuestions.currentTask](../../../../src/main/java/me/asu/aidev/questions/NativeQuestions.java:42) 校验正式 APPLIED 问题、Owner、原 source 摘要、实际 slot、源任务状态、目标作用域和原尝试，再解析实际 successor。guarded-v1 入口明确保留 execution_context/TaskLineage 路径，不被 native 解析器接管。[WorkflowPlanService](../../../../src/main/java/me/asu/aidev/workflow/application/WorkflowPlanService.java:398) 与完成 handler 的纠错依赖统一使用实际完成成果。新增真实 SQLite、NativeQuestions/NativePlanOwners/FormalQuestions 与 JdbcExecutionAttemptRepository 组合用例，不再仅靠 mock 假设来源能力。

静态复查认为当前调用链正确；native 真实 SQL 用例在 54 项那轮已执行并通过，后来新增的 guarded-v1 兼容用例目前仅编译，未运行。

### R2 — P2：SELF 的人工评审恢复与最终完成门相矛盾（已静态修复）

初始实现允许 SELF/REPAIR_REQUIRED 经显式人工恢复获得独立 review PASS，并据此推进下一步，但最终完成门又要求包括原执行报告在内的所有输入都是 PASS，导致单步无法完成、多步最后被原自检报告卡住。

修复在 [completeReviewed](../../../../src/main/java/me/asu/aidev/workflow/application/WorkflowPlanService.java:448) 继续要求成果真实完成且有报告，并按固定策略核对验收。只有原 SELF 已被独立 review 接纳时可以保留原 REPAIR_REQUIRED；不重写原报告。首次修复曾过宽允许 Independent 执行 REPAIR，由旧守卫用例指出；最新实现已将例外收窄到 SELF，Independent/Milestone 继续保持原执行 PASS 要求。

当前窄化条件静态复查无阻断，但最后这一生产条件修改后的测试尚未获新增授权执行，不能把此前 53/54 记为通过。修正反馈的来源标签也已区分 self-check 和 independent review，不虚构历史独立评审。
