## 发现

**P1：新增进度事件不符合现有机器通道白名单，提醒阶段就会拒绝事件批次。** `progress_monitor.py` 的提醒与停止事件新增 `tool=last_tool`，实际值是 read/grep 等小写工具名；停止事件还新增 `status="stopped"`。`RunChannel.observe()` 对 progress-stalled 没有规范化，按 FIELDS 原样转发 tool/status。`RunContract.metadata()` 的 tool 仅允许 MODEL/READ/SEARCH 等大写分类，status 也没有 stopped。本提交未同步修改该契约。

因此第一次提醒即可在 `ExecutionRuns.events()` 的 metadata 校验中被拒绝，而不是可靠记录提醒并继续；达到阈值后的 stopped 同样非法。RunChannel 的 watcher 将422记为 RUN_CHANNEL_REJECTED，后续通道/静止确认可能失败并转为资源结果不明，掩盖预期 MODEL_NO_PROGRESS 正常失败链路。纯 ProgressMonitor 用例没有覆盖序列化后到 Java 白名单的真实契约。

最小修正：对 progress-stalled 将实际工具名映射到已有安全 toolName 字段（或映射成合法 tool 分类），并将 stopped 映射成既有合法状态，或明确同步 Java 白名单。保留 code 区分提醒/停止，不能删除安全 metadata 校验或转发原工具参数。复核只需覆盖该映射及受影响通道，不要求运行测试或新验证门禁。
