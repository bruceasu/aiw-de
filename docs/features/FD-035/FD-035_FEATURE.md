# FD-035: 工作问题与人工控制改为清晰的问题收件箱与分区操作

**Status:** Open
**Revision:** 3
**Priority:** Medium
**Evidence policy:** Dual

## Problem

用户反馈“工作问题与人工控制”UI 不友好。现有 /ui/questions 将完整问题、任务状态和 Telegram 状态直接打印为 JSON，普通回答与授权回答均要求手工理解原文/版本；问题、执行控制、绑定和预算追加纵向堆叠，没有明确待办、选中详情或操作结果。用户此前明确要求页面分区切换，并在系统运作前让预算默认仅记录。

## Options and decision

- 仅美化原 JSON 区域：无法消除接口阅读负担，不采用。
- 改写问题/执行服务：超出 UI 请求，影响已有多渠道事务，不采用。
- 保留写接口和权限语义，改为问题收件箱、结构化详情/回答、可切换的任务与控制、通知设置。采用。沿用 Web Console 外壳与现有主题，仅增加页面只读计划标题和部署计量模式。

## Solution

### 操作路径

顶部选择当前账号的计划，优先显示可取得的目标标题并保留 ID 辅助辨认；没有计划时给出真实授权入口，不留空按钮。显示待处理问题、等待推进问题、任务执行状态摘要。三个键盘可切换面板为“问题收件箱”“任务与人工控制”“Telegram 通知”，导航在长详情中保持可达。

收件箱提供待回答、等待推进、处理记录和全部筛选，左侧简短问题列表，右侧显示当前选中问题：问题原文、回答要求、必要上下文、建议选项、来源、已有原始回答和阻塞原因。原回答区分人类/秘书和渠道，内部 ID/版本仅折叠为来源信息。原始响应不作为 JSON 展示。建议选项可填入回答草稿，仍需显式提交；专业问题使用文本回答，授权问题使用明确“批准此申请/拒绝此申请”按钮及具体维度、追加量、累计上限，不让人输入 APPROVE/REJECT。只有原服务允许覆盖的未生效秘书回答才提供填写原因的显式覆盖入口；已经生效或人类已回答时展示事实，不提供必然被拒绝的改写表单。

计划执行状态采用中文任务列表和暂停/已取消/可准入状态；停止请求与实际停止确认分别显示，不能把点击取消描述为进程已停止。取消操作通过现有 Console dialog 样式明确目标计划和影响再提交；暂停/恢复解释用途，已撤销计划不提供恢复。默认 record-only 隐藏追加申请表单并说明只记录；部署 enforce 时折叠提供原申请能力，使用中文维度和单位，仍按原始单位及精确累计上限提交，不改变预算准入语义。

Telegram 显示真实绑定用户/私聊、送达状态及未知结果，不展示原始 JSON。绑定在当前账号所有计划间共用，改绑/解绑必须明确全部影响范围；读取仅包含该账号最近 100 条送达，问题需按 questionId 匹配，达到 100 条时不能以未见记录推断无送达，应禁止新发送并说明记录不完整。明确告知绑定不等于 Bot 已启用；本 FD 不启动 Bot 或发送真实消息。只允许人类逐题点击发送。已有未结束送达 READY/SENDING/UNKNOWN 或仍有效 DELIVERED 时不提供重复发送；失效或过期后才可明确发起新送达，UNKNOWN 不因过期自动重发。改绑/解绑说明旧消息关联失效，解绑需确认，没有绑定时不可解绑。

### 状态、并发与写入边界

任何读/写请求捕获原计划；计划切换立即清空旧详情/版本，使用序号及捕获的计划校验，旧响应不能填入新计划。写入中冻结计划选择、相关字段及重复按钮。普通刷新保留按计划/问题身份保存的未提交草稿及原问题/回答版本；版本改变时禁止把旧草稿静默提交为新版本，要求明确重新核对当前问题后才采用其版本。草稿只在当前页面内保留，不声称浏览器重启恢复。

写请求捕获精确 body；回答 messageId 和预算 requestId 在未知结果期间保持，不自动生成新 ID 或重放。连接/5xx/无法解析响应视为结果未知，冻结新写入，先刷新同一计划核对。回答可用同 messageId 的原回答证明已记录；额度申请可用 requestId 对应的正式问题证明已登记。不能证明原操作完成时保留“结果未知”，明确由人类核对后结束此次核对；只有有幂等身份的回答/额度申请提供显式重试原 body。控制/绑定/送达没有同等请求身份，不提供自动或一键原请求重放。返回明确成功后，后续刷新失败单独提示，不能将成功写入描述为失败；刷新失败或计划未成功读取时禁止新版本敏感写入。Telegram 单独读取失败不能抹掉已读取的问题，但通知写入不可用。

### 服务及兼容

仅在 AuthorityPageController.questions 增加当前 Owner 已有计划的可读标题选择项和 ExecutionAccounting 模式模板变量，保留 questionPlans。可取得的 WorkflowPlan 必须同时属于当前 actor；无标题回退现有 ID。所有写 DTO、current human/Owner/角色/CSRF、正式问题版本及消费/停止确认事务完全沿用。无新表、迁移、依赖、API 路径或后台轮询。权限相关按钮与服务端既有规则对齐，不授予新权限。授权问题使用 authorization 的结构化范围，不直接显示服务端拼接的机器 context；版本、增加量和累计上限要求浏览器安全整数，超出精确范围时明确提示并禁止相关提交，不展示舍入后的伪精确数值。

## Scope

questions.html、questions.js、新 question-controls.js / questions.css、AuthorityPageController 的 questions 方法、共享导航中的问题入口、docs/FORMAL-QUESTIONS.md 和相关稳定 UI 规格。questions.js 持有唯一的读取/原请求/草稿协调状态，控制与通知脚本复用它，不复制请求状态机。继续沿用当前主工作区的范围提交方式，保留 FD-033 未决草案及其它私人秘书、模型和启动脚本改动。

不改变授权范围、服务端事务、Telegram 传输、预算默认模式或任务执行。不运行测试、浏览器、数据库、服务、模型、真实 Telegram、网络下载、打包或发布。主要风险是跨计划异步响应、回答版本/覆盖与未知写结果；实施前独立静态设计审阅，实施后另行独立实现审阅。

## Acceptance

1. 普通用户能从当前计划查看待回答问题，选中后阅读上下文/要求/原答并明确提交；无需阅读 JSON 或手填内部版本（1.2、1.3）。
2. 计划、问题状态、任务状态、停止请求/确认和通知送达以中文事实显示；空态、读取失败、无操作角色均给出原因；READY/取消请求/UNKNOWN 不被称为执行或送达成功（1.2–1.4）。
3. 三个分区切换显示并可键盘访问；高级预算与通知不挤占日常问题路径，沿用 Console 主题/组件（1.2、1.4）。
4. 专业回答、授权批准/拒绝、秘书回答覆盖均提交精确原版本/身份；APPLIED/SUPERSEDED 及已有不可覆盖的人类回答不提供改写入口。刷新不覆盖草稿，采用新版本需显式核对（1.3、1.4）。
5. 跨计划旧响应被丢弃；写入中禁用重复与切换；未知结果先查同一原记录，有幂等身份才允许显式原 body 重试；已确认写入不因刷新失败变失败；通知 UNKNOWN 不重发（1.4）。
6. 原有接口、Owner/角色/权限、消费及计量/停止语义保持；记录未运行验证及需要更新重启的限制（1.2–1.5）。
