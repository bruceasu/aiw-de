## 发现

### P1：工作流停止未接入实际取消回执，收到 ACK 后任务会重新就绪

位置：`src/main/java/me/asu/aidev/workflow/application/WorkflowRuns.java:275–285`、`:247`。

当前验收要求“停止请求保留实际回执与历史”。`control(stop)` 仅调用 `attempts.requestStop()`，既没有原生 Run 的 CANCEL command，也没有旧 Plan 的 PENDING_STOP control。真实 Worker 发现停止请求后，会调用 `stop-acknowledgement`（`workers/process-python/process_worker.py:716`）。`TaskExecutionService.acknowledgeStop()` 因 `NativeRunLifecycle.cancellation()` 返回 false，进入通常 ACK 分支并调用 `tasks.requeueRevoked()`（`TaskExecutionService.java:281–304`）；该方法将任务置为 READY，而不是 CANCELLED（`JdbcWorkTaskRepository.java:120`）。

结果：工作流仍为 STOPPING、底层 Plan 仍为 CONFIRMED；`view()` 不接受 READY 作为停止完成，所以实际 ACK 无法正常收敛。现有 Worker 还可以再次领取该任务，产生重复模型调用。这是静态可追溯的集成缺陷，并非要求增加测试门禁。

最小修正：复用现有原生取消或 Plan 停止机制，使该工作流的停止回执原子取消当前任务并保留真实证据，且停止请求之后不再重新派发该任务；不能仅在页面上显示 STOPPED 或根据租约消失推定停止。

### P2：通用任务页面没有说明只读文本执行边界

位置：`src/main/resources/templates/ui/workflows.html:18–23`。

FD Solution 明确要求“当前通用 Worker 为只读文本执行，界面明确说明”。实际页面只说明共用执行能力和无需 Git 仓库；简单任务输入与执行按钮旁没有只读、仅生成文字、不能写文件的提示。`general-work.toml` 与下发指令确实禁止写文件，所以当前页面允许用户以为普通文件任务可以执行，实际行为与预期不符。

最小修正：在共用页面增加简短的可见说明，并沿用当前语言切换方式；无需添加新的操作或流程。
