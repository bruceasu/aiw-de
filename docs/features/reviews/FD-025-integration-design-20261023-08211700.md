## 事实、设计前提及边界

实际代码已有独立个人凭证、process boot、显式启用与 generation，`ActionAdmissionService.enabled` 在服务层复验；HTTP 的 personalMachine/humanRoute 与 UI 匹配列表是封闭入口。`PersonalQuestions.proposal` 对旧来源 boot/generation 的严格相等用于执行已有授权问题，不能直接复制成新提案的历史查询门禁。

`GraphPlans.change` 已拥有当前 owner 操作角色校验、UUID/digest 重放、expectedVersion 与图草稿事务；`GraphPlans.state/list` 允许当前 owner 操作/审批读取。ROOT 的 `exports` 和 `exitDigest` 是正式冻结出口，`Fact.digest` 摘要覆盖 TaskInput；Delivery 的实际字段为 baseline/resultRevision/changes/commandsRun/checksNotRun/unresolved/sources，配置摘要需从固定 context/配置引用核对，不假设 Delivery 存在另一个 configDigest 字段。

尚未实现的设计前提：V16 只新增平台提案与采纳收据；私人端复用已有 `decision` 记录及 CAS 历史。当前 `personal_outbox` 的 reconcile 在特定 404 后会重发原 action，而目标提案明确要求 UNKNOWN 只查询，因此新提案不应进入该 outbox 或修改其原行为。

## 最低实施合同

### I025-01：最小投影、当前身份与可恢复的只查询状态

状态为本轮已明确解决的设计细化。`GoalProjection` 只接受 selectedGoal/necessaryContext/acceptance；selectedGoal 必填，其他字段可省略，限制长度、NUL、未知字段和整体 envelope。预览在私人本地生成固定 UTF-8 JSON 原文及 SHA-256，不访问平台、模型或读取未选聊天。确认绑定该原文与 digest；正文变更须重新预览确认。

提交由 HTTP 独立凭证及当前 worker boot 识别调用者，服务在同一 authority 锁事务内调用 enabled 并重新核对当前 owner/worker/generation/平台启用 boot/worker boot。owner 与 worker 来自认证上下文，不相信正文自报。没有现成 PLAN target 时不调用要求其 read_scope 的 readable，不引入 A01/grant，也不调用图、Factory 或模型。严格只开放指定 POST、canonical UUID GET 与人类 UI/read/adopt；新 UI 必须同时进入认证拦截匹配集合。

平台键为 owner+requestId，原 worker、projectionJson、digest、平台 instance、原 boot/generation 固定。计算 SHA-256 必须用收到的 projectionJson UTF-8 原文，不能先重排或重新编码再比较；相同 ID 异原文、异 worker 拒绝，合法重放只返回原收据，不改来源。原 boot/generation 是历史来源，查询旧回执使用**当前已启用、同 owner+worker** 的身份校验；不要求旧 boot 仍等于当前值。平台 instance 改变必须保留私人绑定冲突，不能跨新平台猜测成功。

私人 `decision` 原子 CAS：PREVIEWED → SENDING，发送前冻结 requestId/raw/digest/instance；一次成功 CAS 仅允许一次 POST。收到且核对匹配的权威收据后为 RECORDED；丢响应、解析或身份不一致为 UNKNOWN。重启遗留 SENDING 按 UNKNOWN 处理；SENDING/UNKNOWN 后只 GET 原 ID，404、超时或被拒均不改为可重发，也不自动换 UUID。查询得到收据还须核对 instance、owner/worker、requestId、digest。此流程不复用 queue/received 的 action outbox 路径，不改现有 action reconcile。

### I025-02：当前人类授权、原子采纳与不可变回执

状态为本轮已明确解决的设计细化。建议人类输入为 proposalRequestId/digest/planId/采纳 requestId，owner 取当前人类所绑定的真实 owner。进入同一个 authority 锁及数据库事务后，先校验**当前** owner 操作角色，再读取提案和已有采纳收据；重放也要重新过当前角色门禁。审批只读角色不能因存在旧收据而获得采纳能力。

已有采纳时，只对照原 proposal/digest/planId/请求业务摘要，返回原 plan/version；不读取当前图 head 来重建 change，不覆盖其后的人工编辑，不允许同提案换计划。首次采纳冻结一个稳定 Graph Change UUID、服务端 source/reason 和精确空 Spec，调用原 `GraphPlans.change(expectedVersion=0)`，随后以唯一 proposal 绑定/CAS 保存原 change 与采纳收据；任一步失败整笔回滚，不存在“有图无采纳”或反向窗口。不同采纳请求竞争同一提案时仍只得到一个原计划；planId 已存在冲突不留下采纳记录。

Spec 仅映射选定三字段；缺范围/验收以明确“待澄清”文本满足数据必填，ROOT 无节点/入口，保持不可激活的空 DRAFT。人类后续沿原图服务规划、审阅及激活。惰性提案既不是委托或目标授权，也不能被秘书当作修改/执行入口。只读聚合先通过 GraphPlans 当前 owner/操作或审批边界，再按该 owner+plan 读取准备、问题、账本和分类；不把私人数据库或其他 owner 的同名数据拼入。

### I025-03：最终出口到真实交付的核对算法

状态为本轮已明确解决的设计细化。读取聚合与证据应处于同一只读事实快照/受控锁事务，避免拼接不同提交状态。仅当 rootActivation 存在、ROOT 为有效最终成功出口时，从该 ROOT 当前冻结 exports 枚举；按 GraphRunner 同一序列化合同复算 exitDigest，再验证每个 Fact 的 executionId、kind、digest。ANSWER 是问题事实，不能充当软件 Delivery；空 TaskInput 集合明确显示“没有软件交付证据”，不作空集合全部通过。

对 COMPLETED Fact：按冻结的 taskId+attemptId 精确读取，按同一 TaskInput 序列化复算 Fact.digest，并逐项核对真实 COMPLETED Task/Attempt、repository、base/result commit、changedFiles、verdict/summary 及 graph execution 映射。核对 context.plan/owner、input_json 原文的 input_digest、固定 snapshot task/input 与 config_digest/配置绑定；Delivery 必须属于同一 Task/Attempt，原 delivery_json 的 SHA-256 等于表中 digest，baseline/result/changes 与冻结输入和真实 Attempt 一致，且每个固定 source 的 id/revision/hash 完整匹配。额外声明 source 不算作已授权固定输入。新图缺 attemptId、完整 baseline/result 或任何必需来源均标缺失，不回落 latest/lineage 猜测；原 CONTINUED 只作历史，最终真实 successor 才是成果。

按精确 taskId+attemptId 去重；同键异摘要是冲突。旧轮、失败、被替代执行及私人状态不能补齐出口。证据缺失、hash/关系冲突、未决效果/计量应分别显示，不补造 Delivery 或改写 ROOT。Graph COMPLETED、证据可核对与业务 verdict/unresolved 分开显示，REPAIR_REQUIRED 不推断成业务通过。commandsRun/checksNotRun 仅展示 Worker 原记录；空缺写“未记录”，字符串中的 passed 不升级为平台独立验证。视图不创建第二份账本，不发布、push 或部署。
