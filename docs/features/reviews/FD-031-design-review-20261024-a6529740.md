# FD-031 独立设计审阅

建议：**changes-needed**。有两个需要 Planner 明确并落实的恢复与确认边界；不需要重新询问已确认的桌面产品范围。

## 发现

### D031-01：安排表单没有固定用户正在确认的工作内容与版本

- 严重度：P1；设计就绪前需要解决。
- 位置：FD 的“操作与失败恢复”、Acceptance 5；`desktop.py:231`、`desktop.py:488`、`desktop.py:512`、`desktop.py:517`。
- 事实：安排表单只有工作标题选择、自动版本和时间。普通状态更新会调用 `update_schedule()`，把同一工作的新版本直接写入表单；没有展示该版本的正文与关联 Plan，也没有区分用户主动载入与后台操作后刷新。
- 影响：用户选择工作并录入时间后，Web 或运行时可能已经改变工作正文、Plan 或状态；桌面读取最新状态会悄悄更新待提交版本，使服务端 CAS 检查通过。版本检查仍存在，但无法证明用户确认的是变化后的内容。
- 最小修正：把安排编辑器绑定到明确载入的工作 ID、版本及可见内容快照，展示正文、Plan 和状态。普通状态刷新发现版本变化时标记冲突并要求显式重新载入、核对；不得只替换版本字段。不同工作选择可以明确载入新快照。
- 验收例：桌面选择版本 N 并填时间，Web 把内容改为 N+1；桌面刷新或其他操作返回后，原安排不能携带 N+1 静默提交。重新载入后能看到新内容，并需再次确认。

### D031-02：单个目标预览槽不能支持退出或重新预览后的原请求恢复

- 严重度：P2；设计就绪前需要解决。
- 位置：FD 的“提交尝试后只允许查原 ID”和 Acceptance 6、7；`desktop.py:617`、`desktop.py:627`、`desktop.py:638`、`desktop.py:704`；相邻持久化合同 `selected_goals.py:14`、`selected_goals.py:24`、`selected_goals.py:72`。
- 事实：目标查询只使用当前只读 `goal_request`；再次预览会覆盖该 ID，退出桌面会丢失整个编辑器。后端已把精确 ID、投影、摘要及状态保存在 `SELECTED_GOAL` decision 中，但设计没有定义如何选回这些记录。原 ID 可以在完整状态中人工寻找并交给 Web，当前文档没有提供这条具体恢复步骤。
- 影响：一次提交超时、随后退出重开或重新预览后，桌面用户不能直接查回原请求；“下次核对原回执”的退出提示缺少可操作的恢复入口，容易把新预览误当成原请求恢复。
- 最小修正：复用 `/api/state` 已有 `decisions`，提供按目标摘要、状态与原请求 ID 选择历史提案的入口，加载精确持久记录后只查询该原 ID；新预览与原请求查询槽分开。至少必须让 SENDING、UNKNOWN 和已记录请求在重配后可找回，不新增业务数据库或自动重发。如果只提供 Web 恢复，需给出明确可执行的定位和原 ID 查询入口，不能仅提示“查看回执”。
- 验收例：提交后丢失响应，退出并重新配对桌面；能从已有决策选中原 ID 进行查询。新建另一个预览后，原 UNKNOWN 仍可查询；查询失败不会重新调用提交。

## 已支持的设计方向

- 鉴权：新配对入口位于现有 Host、Origin、独立私人会话及 CSRF 检查之后；登录仍受服务锁保护，五分钟、五次、一次性规则未被绕开。生成新码只替换未使用码，不复制、撤销或延长已有会话。
- 桌面客户端：仅本机显式端口，独立内存 CookieJar，不使用环境代理或重定向，不直接访问平台、SQLite 或浏览器 Cookie。POST 成功后的状态读取失败被作为“结果已返回、状态待刷新”处理，没有自动重放。
- 窗口职责：Tk 主线程处理窗口，单次后台请求通过队列返回；Win32 适配只拥有位置和托盘。隐藏失败回退、托盘恢复失败显示人物和退出 UI 不结束 Worker 的方向清楚。透明边缘、多显示器和 Shell 重启表现仍需运行证据，静态代码不能证明。
- 精确确认：目标原文、摘要与 ID 直接来自预览响应；编辑版本校验避免迟到预览覆盖新输入。服务端在原 ID 上 CAS 到 SENDING，再进行一次平台提交，UNKNOWN 查询不重放。策略载入和保存后取消勾选确认，已有策略标识锁定，不从旧回执推导禁止投影。
- 产品范围：Web 保留完整资料、正式问题、备份和取消，桌面是新增 UI；不引入启动 Worker、自动启用、语音或多姿态动画。

## 独立 Web 配对适配器的补充边界

父会话在本轮审阅中提出把配对卡片事件移入独立 `pairing.js`，避免依赖同一工作区中其他 Web 改版。这个责任边界可行，以下是设计约束，**不是已完成实现证据**：

- 仅显式生成时 GET `/api/state` 取得当前会话 CSRF，再 POST `/api/pairing`；使用同源会话，不自动登录或重试 POST。
- 不引用 Web 重构的全局选择器、状态对象或 `post()` 返回结构；使用卡片内反馈。
- 配对码和令牌不落 URL、日志或配置；显式显示/复制，到期清空，失败不隐式生成替代码。
- 由私人服务静态资源白名单提供该脚本，不改变平台凭证与 Worker 生命周期。

没有据此新增第三个阻断项；实际适配器待 Worker 实现及实现 Reviewer 核对。

## 工作项与证据覆盖

现有 Acceptance 已映射到工作项，正常配对、人物操作、对话与授权边界基本齐备。建议保留已勾选的 1.4 为准备历史，把上述两个修正拆成稳定子项，分别记录规模、难度、依赖和完成证据；同时给独立配对适配器单独结果项。不要因历史勾选而把待修正行为视作验收通过。

Acceptance 和 Verification 应加入上述冲突、重开恢复例，以及“配对 POST 已成功但状态刷新失败”“迟到目标预览被丢弃”“托盘初始失败或 Shell 重启失败仍有可见入口”例。测试未被授权，记录这些场景不等于已执行；可用静态证据进入后续实现审阅，但必须保留运行限制。
