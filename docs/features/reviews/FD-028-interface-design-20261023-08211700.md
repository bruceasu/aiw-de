# FD-028 实施接口独立设计反馈

建议：**changes-needed**。新增接口方向符合已确认的业务语义，但下列四项工程接合仍须固定，才能据此实现。它们是本次补充设计的就绪问题，不是对尚未实现功能的缺陷判定；此前 D028-01/02 的设计复查历史保留。

1. **I028-01 / P1：checkpoint 尚缺可执行的冻结、登记和取回合同。** 位置：FD 第 89 行；`ExecutionYieldService.continueTask`、`GuardContract.Yield`、Python `GuardBroker` / `GitWorkspace.materialize`。事实：既有继续原语要求续行 baseRevision 与源任务完全相等；Yield 的 checkpoint 只是 FrozenRef。现有 Worker 只从正式上游成果取回输入，然后按任务基线建工作区；“本地真实提交”本身不能保证另一 Worker 或重启后的执行器可以取回。设计还未说明创建 checkpoint 时如何先排空写入，避免提交后仍有在途工具修改工作区。

   最小修正：固定顺序为 broker 停止接纳新模型工具调用 → 等待已有调用得到确定结果 → 按既有许可制作最终 checkpoint → 以精确 Lease 持久登记 checkpoint 和 yield 意图 → 停止模型及全部子进程 → 真实静止 ack。checkpoint 至少固定源 task/attempt、仓库、原基线、不可变提交、内容/证据摘要和登记操作；继续只从该源已确认 yield 的 checkpoint 或原基线选取，保留其余配置、政策交集及上游输入，不能只凭任意 Git hash 放行。明确受控继续原语的窄扩展，并给 checkpoint 独立的持久保留及取回接口；不伪造成已完成 TaskInput，不接受模型任意下载地址。只读/无更改任务复用原基线；脏工作区只有现有写入/Git 许可允许时才制作提交，否则保持阻塞及现有资源，不隐含新增权限。

2. **I028-02 / P1：LEGACY_PLAN_TASK 需要明确覆盖已交付的 configured-plan。** 位置：FD 第 67、90 行；`AgentFactory.prepareAuthorized`、`WorkflowQuestionService.plan/board/answer`、`WorkflowTaskPosition.parse`。事实：FD-027 创建 `subject_type=configured-plan`，subject_id 是真实 execution_policy.plan_id，不要求 flexible_workflow_plan；现有 WorkflowQuestionService 则以 WorkflowPlan 和旧任务 ID 语法为入口。若“真实 plan/task/attempt”被实现为统一查询旧 WorkflowPlan，首期配置任务无法提问和续行。

   最小修正：将 LEGACY_PLAN_TASK 明确定义为“现有受控任务来源”，封闭允许 configured-plan 与 flexible-plan。共同验证 owner、真实 execution policy、task.subjectId、guard context 的 plan/task/配置关系，以及精确 Attempt/Lease；已 yield 后用所登记的原 Attempt，而非猜测下一 Attempt。configured-plan 额外核对已登记配置绑定；flexible-plan 额外核对真实 WorkflowPlan/版本/步骤及 lineage 逻辑槽。非受控旧成果问题可保留原服务入口，不能因回答自动获得新 guard 授权或新续行。WORKFLOW_GRAPH_EXECUTION 仅通过 FD-026 注册 resolver；未注册则明确拒绝。业务槽沿 lineage，Lease 定位原任务；不伪造旧 WorkflowPlan，不引入自由第三种 sourceRef。

3. **I028-03 / P2：A19 的问题快照、投影绑定及暂停边界须固定到现有 admission。** 位置：FD 第 91、93 行；`ActionAdmissionService.apply/businessDigest`、`AuthorityActions.key/snapshot/admit`、`ActionScope.parameters`。事实：现有授权以参数全等、expectedSnapshot、目标世代和原 requestId 回执为依据，evidence 已进入业务摘要；默认动作却会查旧 WorkflowPlan，并经过目标 paused 门禁。新增句子尚未说明 A19 的封闭参数与快照，也未区分工作暂停和委托身份禁用，容易把“保存答案”接到“推进工作”的准入上。

   最小修正：为 A19 明定问题 ID、requestVersion、expected answerRevision 及真实来源标识的封闭参数/快照，复用真实 owner/目标读取范围，避免落入默认 WorkflowPlan 分支。投影以平台实例+owner+个人 Worker+requestId 唯一登记，内容包含明确选择的原始问题关联、原始回答及摘要；记录真实 boot/身份，重登记内容冲突拒绝。admission 在自身事务内按原 requestId 取该投影，校验 evidence 摘要、owner/目标/问题版本，并原子写回答历史、ANSWERED、用量与原回执；不改参数全等规则、不改写原答。登记只检查身份/读取范围且无业务效果，外层不包事务。执行暂停允许保存答案，APPLIED/继续仍受当前 guard 控制和预算；委托禁用、撤销、限制或人类接管仍拒绝秘书决定，不能以“暂停例外”绕过。A18 另外绑定具体额度申请和唯一追加回执。

4. **I028-04 / P2：复用 poller 还须固定持久收件及发送崩溃窗口。** 位置：FD 第 92 行；`TelegramApprovalAdapter.pollLoop/handleCallback`。事实：当前只有进程内 AtomicBoolean 和内存 offset，处理 update 前即递增 offset，只分派旧审批 callback。直接增加新 handler 不能证明重启/处理失败时不丢问题答复，也不能证明新问题不会进入旧审批路径。

   最小修正：同一 bot 仅一个接收分派器；明确单实例运行前置及重复启动拒绝，若支持多实例则有独占所有权/接管方案。先以 bot 身份+updateId 将最小原始 update 持久收件并去重，成功提交后才推进持久 offset，再按封闭类型交旧审批或新问题消费者；各消费者在自己的幂等事务复验 owner/user/private-chat/generation/关联/问题版本。文字回复必须匹配已登记送达 messageId；callback token 同时校验当前绑定与问题，未知前缀不落旧审批。outbox 固定 READY→SENDING→DELIVERED/UNKNOWN/INVALIDATED：发送前 CAS 并复验绑定，真实响应保存 messageId；外部结果或提交确认丢失、以及重启遗留 SENDING，均进入 UNKNOWN，不自动重发。未知 messageId 不接受文本猜测关联；通过人类核对或新显式决定处理，不清空原证据。

已闭合的方向：原始投影登记与动作 admission 分离能保留现有失败回执事务；一个问题/回答历史/APPLIED 所有者能避免渠道各自推进；早答暂存、yield 后继续、CONTINUED lineage、取消先阻止准入并等待停止确认，以及不走旧 Git 回滚均符合当前约束。上述修正属于工程合同，不需要重新决定最小投影、双后端、预算等待或 UNKNOWN 政策。
