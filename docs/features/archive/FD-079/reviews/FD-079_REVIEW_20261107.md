## 发现及修复复核

### R1 — P2：切换 guarded 任务后仍可能控制旧尝试（已解决）

原 `worker-run.js` 仅监听自身选择器。上方 `wb-task`/`wb-attempt` 变化后，旧状态和可用按钮可能维持到下一次轮询，点击会按旧 `state` 提交控制，违反当前选择与控制目标一致的要求。

修复在 [worker-run.js](../../../../src/main/resources/static/ui/worker-run.js:13) 增加 `aligned()`，用于控件、点击和提交前身份检查，同时监听两个上方选择器，立即清空并重绘状态。旧请求重试也须对应当前选择。静态复核确认关闭该窗口；浏览器操作未执行。

### R2 — P2：通用问答能力被误用为必须恢复 checkpoint 的标记（已解决）

原 `_load_checkpoint` 看到任务要求 `questions-v2` 就强制非空 checkpoint。首次任务可以合法要求这种适配器能力，却没有来源 slot；原逻辑会在模型执行前拒绝，并将资源标为未知。

修复由 [ExecutionRuns.availability](../../../../src/main/java/me/asu/aidev/execution/run/ExecutionRuns.java:218) 在精确来源/租约校验后，根据正式 successor slot 返回 `checkpointRequired`；[native_run.py](../../../../workers/process-python/native_run.py:118) 严格检查该布尔声明。首次任务可要求问答能力而不恢复；真正续行缺 checkpoint、首次任务收到意外 checkpoint、缺失声明均拒绝。已检查相应 Python 规则用例与 Java SQL 用例，未弱化固定交接、确认答案和存储/模型约束。

### R3 — P2：上下文分页工具绕过软暂停计数（已解决）

原 `read_context_source` 只有取消检查，没有运行通道准入。MODEL 已结束、活动计数归零并确认暂停后，SDK 仍可调用这个宿主数据工具，违反 TOOL 暂停边界。

修复在 [openai_api_runtime.py](../../../../workers/process-python/openai_api_runtime.py:424) 使用 `local_read`；[run_channel.py](../../../../workers/process-python/run_channel.py:134) 的异步入口和同步入口复用同一短临界区。等待使用异步 sleep，成功准入后至同步有界读取和 `finally.leave()` 之间无 await，也没有后台线程可能在取消后补记准入。相应规则覆盖等待时不读取、读取期间活动计数为 1、取消等待不读取且不泄漏计数。不新增 CP 文件或工具授权。
