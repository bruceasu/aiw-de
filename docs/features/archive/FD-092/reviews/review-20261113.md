## 阻塞发现

### P1：停止请求与输入回执竞争时，正常拒绝被误判为资源结果未知，阻断停止确认

位置：`src/main/java/me/asu/aidev/execution/run/ExecutionRuns.java:231–237`、`src/main/java/me/asu/aidev/workflow/application/WorkflowRuns.java:367–371`、`workers/process-python/workflow_inputs.py:14–24`。

当前验收要求停止后不启动额外调用，并保留原租约、Attempt、批次的真实回执。考虑以下合法顺序：Worker 已 RESERVE 补充批次并开始模型请求；用户请求停止；模型请求恰好完成，Worker 尚未通过心跳观察停止，尝试 ACK。`workflowInputs()` 对所有动作使用 `machine(..., true)`；`ExecutionGuard.verifyLease()` 的 running 检查拒绝已设置 `stop_requested_at_epoch_ms` 的 Attempt。即使放宽这层，`exchangeInputs()` 仍会对 STOPPING 状态统一拒绝 ACK/UNKNOWN/DRAIN。

Python `_post()` 把这个确定的服务端拒绝也设置为 `attempt.resource_uncertain=True`。随后 `process_worker.py:713–716` 明确跳过失败/停止回执，并保留资源。结果是：已经收到模型终态却无法记录批次状态，且停止流程可能永久保持 STOPPING，而不是在原有停止 ACK 链路中收敛。即便没有批次，模型结束后 DRAIN 与停止并发也会触发相同问题。

最小修正：区分“禁止发起新调用”和“记录既有调用事实”。对原任务、Attempt、批次的 ACK/UNKNOWN 保留精确租约校验，允许记录停止请求之前已经保留的批次事实；停止态 DRAIN 应明确阻止继续模型调用；新 RESERVE 继续禁止。Python 对明确的停止边界结果不能推定外部资源未知。真正网络结果不明仍应保留 UNKNOWN/资源保护，不得直接清除不确定标志或伪造 ACK。

这是静态调用链确认的正确性缺陷，不要求增加架构或测试门禁。
