1. **R029-01 / P1：claim 与 start 之间重新准入，破坏在途语义和并发预留。**
   位置：`src/main/java/me/asu/aidev/execution/guard/ExecutionGuard.java:178`，关联 `ExecutionLedger.java:49`、`TaskClaimService.java:169`。
   `TaskClaimService.claimNext` 成功创建 CLAIMED Attempt 时只检查 `canClaim`，没有持久化 TIME/COST 预留；`starting` 再次调用含 `!paused` 与剩余额度检查的 `canClaim`，随后才 `ledger.start` 预留。静态反例一：claim 提交→用户暂停→start，已领取任务被拒绝；反例二：只剩一个 Attempt 的额度，两 Worker 在任何 start 前均成功 claim，第一个 start 预留后，第二个已领取任务被重新拒绝。Python 此时尚未把 `started` 置真，通常也不会发送 fail，任务和 Worker 槽会滞留 CLAIMED，待 Lease 过期后进入保守人工恢复。
   当前明确合同是先提交 claim 属于在途，暂停/到阈值阻止后续领取与推进，已授权在途可开始及收尾。最小修正：在同一 claim 事务中持久化精确 Attempt 的准入及 TIME/COST 预留；start 仅启用实际计时并复验精确 Lease、授权撤销/到期、固定上下文和未知效果，不因后来的 pause 或其他任务预留而重新否决既有准入。保留真正撤权/停止/UNKNOWN 的阻断，明确未启动取消或过期的预留处理，不能通过删掉安全检查修复。
