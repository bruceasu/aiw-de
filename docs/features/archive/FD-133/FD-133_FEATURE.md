# FD-133: 以执行回执核对任务完成条件

**Status:** Complete
**Revision:** 5
**Review policy:** Independent
**Priority:** Medium
**Evidence policy:** Markdown

## Problem

文件任务可能提交一段成功报告，即使用户要核对的检查失败或没跑。Python Worker 已记录受控命令的配置 ID、退出码和结果摘要，完成校验目前主要检查报告结构，并有一次性命令核对提示。用户需要在任务结果中看到实际检查事实，以及未达标时如何处理。

## Options and decision

复用现有受控命令和完成结果。用户从任务已配置的命令里选出必需检查，任务派发时冻结所选 ID。普通文字条件供 Worker 自检。按命令 ID 绑定回执可以避免用模型报出的类似命令、临时 shell 命令或其他尝试的结果来充抵检查。命令配置和权限仍由现有执行策略管理。

## Solution

简单任务提供可选验收说明，独立保存，与原任务描述分别计数。文件任务配置命令后，可选择其中哪些是必需检查。请求和执行数据用一个可选 `requiredCheckIds` 列表表示明确选择，缺省为空。服务端校验 ID 存在、唯一且任务支持受控命令。新增数据随已有工作流运行快照冻结，不添加单独的持久化表。选了必需检查的任务只派给支持该约定的 Worker，能力不足时给出明确的等待原因。

Python OpenAI 兼容 Worker 在形成最终结果时，把必需 ID 与同一次尝试的现有受控命令回执对应。一次确定结束的受控命令才能产生可用检查结果。按执行顺序使用同一 ID 的最后一份有效回执，保留已记录的历史。退出码为 0 表示对应命令成功。选为必需检查的命令应只验证产物，允许测试生成临时输出。用现有 Broker 记录的文件写操作、Git 整合和非检查命令顺序，使之前的检查结果失效。Worker 可在现有额度内重新检查。该设计按已观察到的动作判断，外部进程改动无法单靠回执证明。存在未确认的操作结果时，沿用中断核对。

完成候选校验向 Worker 提示未达标的必需项。正式交付前再次从回执核对，防止轮次用完时仍提交成功。缺项、非零退出或检查失效使用 `REPAIR_REQUIRED`，工作流停在本步骤并保留报告。Plane 收到 PASS 时，核对正式交付与同任务、同尝试、同命令的受控操作，要求完成状态及结果摘要匹配。必需命令的非零退出记为失败操作，结果仍交回模型。回执体现已认证 Worker 的执行记录，独立验收仍由工作流显式配置。

任务详情复用正式交付里的 `commandsRun`、`checksNotRun` 和已有文件交付引用，显示通过、失败、未运行或需重新检查，以及可定位的配置 ID 和回执。只展示当前尝试可查的内容。缺少证据时显示「未记录」。列表和文案沿用 Web Console 现有中英语言设置。

## Scope

首期覆盖简单任务和 Python OpenAI 兼容 Worker。工作流各节点仍可写文字验收条件。多节点逐步配置必需检查留待验证工作流设计时处理。采用当前命令授权与运行依赖，沿用当前停止和人工重试。任务没有必需检查时按原定完成规则处理。

审批续接可能创建新的执行尝试。若多条必需检查各自需要审批，需合并成一个命令配置，确保同一次尝试能形成完整回执。

## Acceptance

- 文字任务和没有必需检查的旧任务可照常完成。可选命令保持可选。
- 简单文件任务选择两个检查时，只有两项均有当前产物的成功回执才可通过。非零退出、未运行、后续修改使检查失效时，页面指出具体项。之后用有效回执重新核对即可。
- 模型声称成功、临时 shell 运行同名命令或引用上一次尝试，均不能满足必需检查。
- 不支持本约定的 Worker 不领取带必需检查的任务。审批未通过、执行中断或效果未确认按各自原状态处理。
- 使用隔离的新闻样例核对默认日文、显式中文及 JSON 解析和字段。用蓄意缺失或错误的 JSON 验证不会记录成功。
