## P1：配置登记没有核对凭据绑定的 Worker ID

`ConfigurationController` 的 `/api/r1/worker-protocol/v1/workers/{worker}/configuration` 只核对 URL worker 与请求体 workerId 一致，然后调用 `ExecutionConfigurations.registerWorker`。后者在第 181 行按输入 ID 读取 Worker，检查既有能力/runtime 后，直接覆盖该 ID 的 execution_worker_configuration 能力正文和摘要，没有调用新增的 boundary.requireWorker。

可复现请求链：管理员给外部 Worker A 创建接入凭据；已有 Worker B 登记配置和 guarded 能力。持 A 令牌对上述路径发送 `{worker}=B`、`body.workerId=B` 和与 B runtime 匹配的能力正文。WorkerProtocolAccessInterceptor 认证后把 A 放入 ThreadLocal，但不比较目标 ID；Controller 中两个 B 彼此相等；Service 不经过 WorkerService 或租约检查，因此写入 B 的元数据。这违反一份凭据只操作绑定 Worker 的本批契约，也能篡改后续配置兼容性判断所读的数据。

最低修复：在 `ExecutionConfigurations.registerWorker` 写入前使用现有 AuthorityBoundary 按 input.workerId 核对当前身份，保留内部调用与既有能力校验；无需新增权限框架。静态用例应针对 A 凭据上下文与 B 输入的这条真实入口，不要求运行测试。

## P2：Worker 自停接单/离线又落入浏览器会话门禁

`AuthorityHttpConfiguration.leaseMachine` 未列 `/workers/{id}/drain` 和 `/offline`。这两个 POST 虽已通过先执行的 WorkerProtocolAccessInterceptor，随后仍落入 AuthorityHttp 的 human session/CSRF 检查；仅携带自身凭据的 Python ControlPlaneClient 无浏览器会话，会被拒绝，无法调用既有自停接单/离线协议。WorkerService 已有绑定身份核对，但控制器尚未到达。

最低修复：让同一专用 Worker 协议前缀统一委托给先执行的机器认证与服务的 ID/租约校验，或补齐这两个动作；避免两份机器路由清单不一致。已阅该段为专用 Worker 动作，未发现需保留 human-only 的协议方法。该补充列入同一轮，沿用 `FD-112-000003-changes-requested`。
