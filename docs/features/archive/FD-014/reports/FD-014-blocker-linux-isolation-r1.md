以下是具体接口方案，尚未声称已经实现或通过平台认证：

| 边界 | 拟固定的接口 | 完成依据 |
|---|---|---|
| 隔离启动器 | 由部署方固定在任务不可写位置的入口；只接受宿主构造的 CLI、stdio、工作区、认证上下文和政策标识；不接收模型构造的参数 | 入口及 CLI 摘要、受支持 Linux 平台、初始化和关闭传播证据 |
| 可写路径 | Codex 状态只能写入受管内存；已授权的 attempt 源码与工程工件另遵循工作区契约 | 真实文件系统隔离与写入监测证据，不接受“临时目录后删除” |
| 内存介质 | 状态区域及进程匿名内存都不能交换到磁盘，core dump/诊断/备份不保存正文 | 宿主政策及实际部署证据；Worker 不自动修改系统设置 |
| 身份绑定 | 显式 API Key 或 ChatGPT 模式，对应独立认证上下文；在活动会话 drain 后重启 runtime | 有效认证类型、凭据存储/刷新边界、对应服务端政策证据；不记录密钥 |
| 启动准入 | 将平台、CLI/入口、配置来源、认证类型、宿主政策及原始验证工件绑定 | 缺失或变化时在注册/领取/发送正文前拒绝；人工布尔开关不是能力证据 |
| 运行验证 | 隔离边界、派生进程、失败/取消/重启及同政策 Exec 回滚 | 另行授权的具体运行命令与事实证据；Windows 历史报告不能代替 |

具体宿主机制尚未固定：新增每 Worker 的 namespace/内存隔离启动器，与对接已有容器或 VM 的部署约束影响范围不同。在核定平台入口及凭据边界前，1.6.2 不标为 ready implementation，也不擅自加入隔离工具依赖、挂载或更改主机配置。1.6.3–1.6.6 依赖该设计。
