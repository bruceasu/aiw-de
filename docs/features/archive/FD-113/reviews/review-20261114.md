## Findings

### P1：成员版 guidance 与实际启动/续接校验不一致

`TeamMembers.guidance` 对成员模型设置返回 `hash(normal.version + settings)` 版本；`WorkerProtocolV1Controller.delegatedGuidance` 将其发给 Worker。Python Worker 按领取的 aiGuidance.version 提交 start。但 `TaskExecutionService.start` 仍调用 `AiProfileCatalog.select`，后者只接受全局 catalog.version，首次启动即抛出 AI profile version mismatch。

续接也不一致：`NativeRunClaimPolicy.valid` 及 `TaskExecutionService.start` 的 NativeQuestions.validateSelection 仍传全局 guidance。NativeQuestions.pinGuidance 比较原 attempt.ai_profile_version，无法匹配成员版版本，续接会被拒领/拒绝启动。

需在真实领取、启动选择、续接校验链一致使用冻结成员收窄结果，并由服务端核验选择属于该范围；只改响应版本或绕过版本校验不能保证成员范围约束。

### P1：编辑旧成员可静默清空或替换已保存模型范围

`src/main/resources/static/ui/team-members.js` 的 show 只遍历当前 data.modelProfiles 生成选项，旧 settings.allowedProfiles 仅按 id 勾选；保存又按所选 id 从当前目录取完整对象。

如果旧方案已移出当前目录，修改备注再保存会把旧非空 allowedProfiles 变成空列表，后端将空范围视为继承全局范围，静默放宽。如果同 id 的模型/强度已变化，表单会无确认地提交新完整值，绕过“保存完整旧值而非可变名称”的保护。后端直接提交旧值会被拒绝，但页面先替换掉旧值，使这一保护无法覆盖普通编辑。

需保留旧完整值和不可用/已变化选择；要求用户明确重新选择后才采用新方案，不能因编辑无关字段自动清空或改绑。

### P2：经验来源把预先分配当成实际参与

`TeamMembers.evidence` 用 worker_team_assignment 筛节点，没有核对 worker_team_task。显式成员在执行启动时即冻结到所有未来节点；`WorkflowRuns.advance` 在底层 Plan 非 CONFIRMED 时，会在当前未来节点记录 FAILED，且发生在任务创建和 team.bind 之前。因此从未派发给该成员的失败，也可被经验来源接口引用，保存经验时再次调用同一 evidence 仍会接受。

需用现有实际派发关联收窄成员节点集合，同时保留当前 actor/执行归属检查。无需新增状态或模型总结链。
