## Findings

### P1 — 候选采集器会验证并发布自己的输出

`ModelPriceRepairActivation.activate` 在 `ModelPriceCollectorProcess.verifyCandidate` 返回后，只检查观察结果能否生成至少一条规则，随后替换采集器并发布相同观察。候选运行路径会执行候选模块自身的 `fetch()` 和 `parse()`（`workers/price-collectors/runner.py:78-90`）；Java 端校验官方域名、候选返回内容摘要与观察结构，但这些值都来自候选进程本身（`ModelPriceCollectorProcess.java:120-134,194-210`）。它没有独立确认最新页面里的模型、档位、时段和价格数值与候选结果一致。提交的 `test_collector.py` 也没有进入激活验证路径。

因此，结构有效但价格错误的候选仍可能被安装、发布，并用于缺价回填，导致费用估算错误。这不满足“Plane 再验证候选后才安装”的验收要求。

**需要：** 增加独立于候选代码的价格核对方式，并让核对结果覆盖最新页面中的模型、价格、时段及服务条件；核对不通过时不得安装、发布或回填。

### P1 — 自动验证在 Plane 账户权限下执行未信任代码

候选源码通过 Python runner 的 `exec(compile(...))` 执行。Java 启动子进程时使用 `-I`、清空环境变量，并设置了超时及输出上限（`ModelPriceCollectorProcess.java:146-170`），但没有操作系统级文件或网络沙箱。候选的 `fetch()` 在 Java 核验其返回的 URL 之前执行，因此候选代码仍可访问 Plane 账户可读的文件／数据库，并向任意网络地址发请求。

这使自动修复产物在验证阶段就能以 Plane 进程账户权限运行；环境变量清理不足以限制文件读取、文件修改或网络外传。

**需要：** 将候选验证放入受限 OS 身份或等效沙箱，限制文件系统与出站网络；出站请求应由受信任层验证目标后发起。在此之前不能自动执行 Worker 提交的源码。
