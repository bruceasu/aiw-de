## 发现

### R1 — 无沙箱命令可在没有用户确认时访问工作区外资源

`process/spawn` 明确以 Codex 沙箱之外的宿主进程执行 Windows 命令（`workers/process-python/guarded_command.py:115-118`）。当前审批仍按命令名称自动放行：旧风险策略版本 0 对全部 COMMAND 直接免审；版本 1 会自动放行 `mvn test`、`python -m unittest`、`pytest` 等构建或测试命令（`workers/process-python/execution_guard.py:42-85, 241-245`）。这些命令会执行仓库中的构建/测试代码；它们能读取或修改工作区外文件，也可能联网。命令 ID、固定参数和工作目录并不能限制运行代码的文件系统或网络访问。

这不符合已确认的规则：默认不得访问工作区外文件，除非用户明确授权或直接指定。无沙箱可以作为实现选择，但现有自动审批不能提供该边界。Windows 无沙箱路径应要求每次执行明确授权，或仅自动放行经证明不能运行仓库代码且不会越界的命令；同时不能让风险版本 0 绕过该要求。

### R2 — 能力探测没有确认 `process/spawn` 可用

Windows 在 `guarded_command.py:115` 调用 `process/spawn`，但 `guarded_preflight.protocol_capability()` 只要求 `CommandExecParams` 字段（`workers/process-python/guarded_preflight.py:65`）。因此，仅支持 `command/exec` 的 Codex App Server 也可能让 Worker 声明 `guarded-command-v1`；直到实际命令调用才因缺少 `process/spawn` 而失败。启动时应验证 Windows 实际使用的协议方法/参数，避免把不可执行的命令能力报告为已就绪。

### R3 — 缺少 Codex App Server 的提示仍称其用于命令隔离

`ManagedWorkerProvisioner.readStatus()` 对 `CODEX_EXECUTABLE_UNAVAILABLE` 的提示仍写“Windows 命令隔离需要 Codex App Server”（`src/main/java/me/asu/aidev/execution/config/ManagedWorkerProvisioner.java:201`）。本次实现已经移除 Codex 沙箱依赖，App Server 在这里仅用于启动命令。该提示会误导用户去配置隔离；应改为说明 Windows 命令执行需要已安装的 Codex App Server。

## 其余检查

- **命令、cwd 与环境：** Worker 只接收配置中的 `commandId`，实际 `argv` 来自固定策略；Python 映射到当前 Worker 解释器，PowerShell 固定为系统 Windows PowerShell 并加入 `-NoProfile`、`-NonInteractive`。`cwd` 通过 `safe_path(workspace, command["cwd"])` 解析。`process/spawn` 收到该 argv、绝对 cwd，以及 `HOME`、`TMPDIR`、Windows 下的 `USERPROFILE`/`TEMP`/`TMP` 环境映射；App Server 进程本身由 Windows Job Object 使用显式筛选的环境启动。该路径没有 Codex 文件系统/网络沙箱，不能据此推断子命令受工作区限制。
- **超时、输出与取消：** 请求包含冻结的 `timeoutMs` 和 `outputBytesCap`；Worker 也按事件累计字节并拒绝超限结果。取消回调设置 session 中断标记，事件读取中止后进入 `finally` 清理。实际 App Server 对这些字段的执行行为未运行验证；本报告不把代码中的请求字段等同于运行时保证。
- **Job Object：** App Server 通过启动门控在加入 Job Object 后才运行；该 Job 配置 kill-on-close、内存上限与活动进程数上限。清理调用 `TerminateJobObject` 并查询到 `ActiveProcesses == 0` 后才确认进程树已结束；失败时标记资源状态不确定并保留临时目录。
- **Linux/WSL：** 差异仍进入 `group` 分支，使用 sandboxed `command/exec`、cgroup 限额、`cgroup.kill` 与 `populated=0` 收尾。相对基线未发现这次改动削弱该路径。
- **PowerShell 审批：** 风险策略版本 1 下，PowerShell 不符合 `_low_risk_command()` 白名单，会走审批；风险策略版本 0 则在白名单判断前直接免审，这也是 R1 授权缺口的一部分。
