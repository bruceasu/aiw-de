## 发现及修复复查

### R1 — P1：自报连接能力未形成 Worker 授权边界（已解决）

初始 `ModelConnections.forWorker` 仅凭 Worker 自报的 `model-auth:` 能力 hash 和 runtime 选择连接；`claimed` 在没有服务端映射时仍可写入空模型绑定，`access` 也未要求映射。普通 Worker 注册允许自报能力，公开连接引用与 hash 因而不能证明该 Worker 获准使用连接。共享机器 token 也不能区分不同 Worker。

修复在 [ModelConnections](../../../../src/main/java/me/asu/aidev/modelauth/ModelConnections.java:59) 强制匹配服务端 Worker/连接/版本/runtime/模型映射，增加只由工厂发放的私有 proof，保存摘要与认证密文；注册、实际领取和取模型令牌均核对 proof。注册检查在更新 Worker 前执行，实际领取仍在既有 claim 事务内；精确 Task/Attempt/Lease、Owner、模型及刷新后重验继续有效。V31 单独新增 proof 列，未改写 V30；无 proof 的旧绑定拒绝使用，需排空后由工厂重新启动。

复查了 Python 控制通道头、工厂环境和子进程环境：proof 不进入安全详情、任务指令、Codex 环境或工具环境；Git 原有环境白名单保留。当前产品明确只向工厂绑定的 Worker 分发 Plane 凭证；外部 Worker 不能靠自报引用领取。新增定向断言覆盖伪能力、无 proof 的注册/领取/访问拒绝、绑定漂移及子进程环境剔除。

### R2 — P2：崩溃遗留 REFRESHING 无法正常重新授权恢复（已解决）

初始安全投影会将超过 30 秒的 REFRESHING 显示成 REFRESH_OUTCOME_UNKNOWN，但数据库仍为 REFRESHING。页面禁用此状态的刷新操作，而重新登录/导入的保存条件又拒绝所有 REFRESHING，导致崩溃后按照界面提示重新授权仍无法保存。

修复在 [save](../../../../src/main/java/me/asu/aidev/modelauth/ModelConnections.java:115) 的保存事务中按原连接版本、generation 和刷新开始时间 CAS 接管过期意图；新代次阻止旧刷新响应覆盖恢复结果，不重发旧 refresh token。原账户/客户端校验、未过期意图排他、断开优先和 token 重复导入约束保留。新增断言覆盖过期意图的新授权恢复，以及旧刷新晚到不能覆盖恢复代次。

### R3 — P2：已保存目录源变化后仍接纳旧结果（已解决）

初始前端只以 runtime/mode/连接识别目录请求，保存新的 Python/Codex 程序路径或 Codex home 后不失效旧目录；后端分别读取配置与版本，也可能把旧配置结果缓存到新版本键。Codex home 变化可能代表不同本机账户，不能将迟到目录显示成当前来源。

修复在 [FactoryModelCatalog](../../../../src/main/java/me/asu/aidev/modelauth/FactoryModelCatalog.java:37) 使用同一次 SQL 读取的配置/版本快照，并在缓存写入前再次核对版本；[工厂页面](../../../../src/main/resources/static/ui/agent-factory.js:267) 保存成功后失效请求 epoch、清目录并重新查询。已选模型作为待核对的显式配置保留，不自动换成目录第一项。新增断言覆盖来源 A 的迟到目录不能污染 B 缓存。

用户报告的空登录下拉框也在本次邻近修复中处理：模板直接包含四个登录来源，同步脚本按执行方式联动，不等待 API 初始化成功；迟到初始化尊重已提交的页面编辑版本，并更新静态脚本版本。模板选项断言通过；没有浏览器运行证据。
